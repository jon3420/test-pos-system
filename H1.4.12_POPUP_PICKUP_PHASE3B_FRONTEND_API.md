# H1.4.12 Phase 3B — Popup Pickup Frontend & Recovery API

This document describes what was actually built in Phase 3B. It does not restate or
rewrite Phase 3A's numbers or history — see `H1.4.12_POPUP_PICKUP_PHASE3A_API.md` and
`H1.4.12_PHASE3A_TEST_REPORT.md` for those, unchanged.

**This is a release-candidate document, not a production-approval document.** See
`H1.4.12_PHASE3B_MANUAL_ACCEPTANCE.md` for what is still pending human verification
(LINE Developers Console configuration, real-device testing) before this can be called
production-ready.

## 1. `/popup-order` route

Previously a hardcoded `503 POPUP_ORDER_UI_NOT_READY` placeholder. As of this phase it
serves the real `public/line-order.html` file (same file as `/line-order.html`), and all
safety is enforced client-side by `resolvePopupEntryContext()`.

### Entry states

1. **Ordinary entry**: `?session=<public_code>` (or `?campaign=...` / `?store_id=...`).
   Anonymous, no LIFF, no identity. Unchanged from Phase 3A's popup bootstrap.
2. **LIFF landing**: `?recovery_token=<token>&popup_session=<claim>` — no `session`, no
   `recovery_handoff`. This is the shape `buildRecoveryUrl()` embeds in the LIFF push
   URL. `popup_session` here is an **unverified client claim**, used only for a loading
   message — the authoritative session code comes back from `/resolve-target`.
3. **Verified recovery entry**: `?session=<code>&recovery_token=<token>&recovery_handoff=<id>`
   — all three required, or the whole thing is `malformed` and fails closed.

Any other combination (token-only, handoff-only, `campaign`/`store_id` combined with any
`recovery_*` param, duplicate/conflicting query values) is classified `malformed` and
renders a safe, generic error — never falls back to standard ordering, never assumes
`store_001`.

## 2. Identity: token is not identity

```
recovery token  -> locates the token row / store / page type only
LINE ID token   -> proves the LINE user's identity (verified server-side against
                    LINE's real /oauth2/v2.1/verify endpoint)
member_session  -> issued only after that verification, store-bound, same format
                    and same primitives (createMemberSession/verifyMemberSession) as
                    the existing standard member-login flow
```

Nothing client-supplied (`store_id`, `line_user_id`, `page_type`, session code, target
path) is ever trusted by any endpoint below — each re-derives its own authority from the
token/receipt row and fresh database state.

### Endpoints (all store-blind — store id is derived from the token row, never the client)

| Endpoint | Purpose | Changes token status? |
|---|---|---|
| `POST /api/cart-recovery/liff-config` | `{recovery_token}` -> `{liff_id}`. Fails closed if `line_popup_liff_id` isn't configured. | No |
| `POST /api/cart-recovery/bootstrap-member` | `{recovery_token, line_id_token}` -> `{member_session}`. Verifies via `verifyLineIdToken()`. Retry-safe. | No |
| `POST /api/cart-recovery/resolve-target` | `{recovery_token, member_session}` -> `{page_type, target_path, popup_session_public_code?}`. Generic across all three page types. | `bound -> opened` (idempotent for the same verified user) |
| `POST /api/cart-recovery/prepare-popup-restore` | `{recovery_token, member_session, popup_session_public_code}` -> canonical cart + one-time `restore_receipt`. | No |
| `POST /api/cart-recovery/commit-popup-restore` | `{restore_receipt, member_session, popup_session_public_code}` -> `{consumed:true}`. Single transaction. | `opened -> consumed` |

All error responses are non-enumerable.

## 3. `invalid_snapshot` vs `valid_empty_after_reconcile`

- **`invalid_snapshot`** (HTTP 400, no `items` field): the stored snapshot itself is not
  trustworthy — malformed JSON, wrong types, non-positive/non-integer quantities,
  aggregation overflow, or more than 50 unique line items. No receipt created, token
  stays `opened`. The frontend shows a distinct "cannot read original cart" message and
  never offers an empty-cart confirmation for this case.
- **`valid_empty_after_reconcile`** (HTTP 200, `cart_state` field): the snapshot passed
  structural validation but fresh reconciliation removed everything. A receipt **is**
  created; the frontend requires explicit user confirmation before committing an empty
  cart.

## 4. Cart snapshot reconciliation

`utils/popupCheckout.js`'s `reconcilePopupCartItemsAgainstFreshAuthority()` is the single
shared function — only `product_id`+`qty` are trusted from the stored snapshot; name,
price, availability, and quota come from a fresh query at prepare time, using the same
eligibility rules as the ordinary popup product listing and checkout itself.

## 5. sessionStorage handoff envelope

```js
{
  version: 1,
  member_session: "...",
  popup_session_public_code: "...",
  recovery_token_sha256: "<64 hex chars>",
  created_at: 0,
  expires_at: 0
}
```

Key: `line_popup_recovery_identity_v1_<handoff_id>` (128-bit CSPRNG, URL-safe). Never
contains the raw token, `store_id`, `line_user_id`, or cart/price data. Read-once:
deleted immediately on read regardless of outcome. `recovery_token`/`recovery_handoff`/
`popup_session` are scrubbed from the URL via `history.replaceState()` in the earliest
synchronous script, before any async work or standard-mode initialization.

## 6. Two-phase cart restore (prepare / commit)

Deliberately stricter than standard `line_order`/`line_shipping` recovery (which never
eagerly consumes on restore at all). Introduced because an HTTP 200 is not proof a
browser actually persisted anything to storage.

1. **Prepare**: canonical cart + one-time receipt, no token state change.
2. Frontend writes to `line_popup_cart_v1_<session_code>`, reads back, exact-compares
   (`persistRecoveredPopupCartStrict()`). Any mismatch rolls back storage to its exact
   pre-write state and keeps the receipt for retry.
3. **Commit**: only after round-trip verification passes. Single transaction — receipt
   and token both become `consumed` together or neither does.

Receipts store only a SHA-256 hash, 5-minute TTL. A partial unique index —
`idx_prr_token_single_prepared` on `popup_restore_receipts(token_id) WHERE
status='prepared'` — enforces at the DB level that at most one prepared receipt exists
per token. Its creation is itself fail-closed: `initDb()` scans for pre-existing
duplicate prepared rows and throws rather than warn-and-continue if any are found.

Concurrency note: `Promise.all()`-based tests prove only same-process competing request
behavior (no `await` points in `preparePopupRestore()`, so Node's single-threaded model
already prevents interleaving) — not multi-process/multi-instance safety. A raw-SQL test
bypassing the application layer confirms the partial unique index itself is the real
backstop regardless of deployment topology.

## 7. Rate limiting

`prepare-popup-restore`/`commit-popup-restore`: 30 requests/IP/60s, same order of
magnitude as the existing member-verify limiter. Limiter state lives in a
`createPopupRestoreRouter()` factory closure; production calls it once.

## 8. What is explicitly unchanged

Standard `line_order`/`line_shipping` recovery (token semantics, consume timing, cart
format, storage key, UI flow) was not modified. `resolveRecoveryTargetForVerifiedMember()`
serves all three page types; `restoreRecoveryToken()` is untouched.

## 9. Known limitations / explicitly deferred

- The real LIFF SDK chain (`liff.init()`/`liff.login()`/`liff.getIDToken()`) is only
  exercised via a test seam — no automated test calls real LINE servers or a real LIFF
  app. See the Manual Acceptance checklist.
- 360px real-*device* visual QA (distinct from a real Chromium browser at a 360px
  viewport, which is covered) is pending.

## 10. RC2 addendum — Security Corrective Audit

- **IP trust model**: all five recovery endpoints' rate limiters now key on Express's
  `req.ip` (respecting `server.js`'s `trust proxy` setting) via a shared
  `utils/rateLimiter.js`, never on a directly-read `X-Forwarded-For` header. Limiter
  buckets are periodically swept and hard-capped to bound memory under a spoofing
  attempt. `resolve-target` gained rate limiting (30/min) — it had none before.
- **`invalid_snapshot` now also covers a raw empty snapshot**: `items: []` at prepare
  time is rejected as `invalid_snapshot`, not treated as reconcilable. `popup_order`
  token creation itself now strictly rejects empty or entirely-invalid cart item lists
  (standard `line_order`/`line_shipping` token creation is unchanged).
- **`liff-config`** now performs a full fresh-authority check (store/license/feature/
  popup flag/session+campaign draft state) via the same SSOT as other popup endpoints,
  and is restricted to `page_type==='popup_order'`.
- **`resolve-target`** collapses every failure cause to one fixed, byte-identical
  response body — the previous version leaked the internal `reason` string despite
  documentation claiming otherwise.
- **`commitPopupRestore()`** verifies each conditional `UPDATE` inside its transaction
  affected exactly one row before proceeding; anything else rolls back rather than
  risking a silent no-op treated as success.

See `H1.4.12_PHASE3B_TEST_REPORT.md` §"RC2 — Security Corrective Audit" for full detail
and updated test totals.
