## 1. What this project is

H1.4.12 is a large feature: a "popup pop-up pickup" (快閃取餐) scheduling system bolted onto an existing POS/LINE-ordering backend (a Node.js/Express app using `sql.js`, a WASM SQLite). It lets a store run a time-boxed "campaign" (活動) containing one or more "sessions" (場次) at a "location" (地點), with its own product-quota rules, and exposes public ordering pages reachable via server-issued `public_code` links and QR codes.

The repository root is `/home/claude/work/extracted`. There is no separate "backend"/"frontend" folder split in the conventional sense — it's a single Express app serving both API routes (`routes/*.js`, business logic in `utils/*.js`) and a static admin SPA (`public/index.html` + the single large `public/js/app.js`, tens of thousands of lines, containing both the general POS admin UI and the popup-pickup admin UI in the same file, namespaced with a `PPA` object and `ppa*`-prefixed function names).

## 3. Phase 3C work in detail — what was actually built and verified

This is reconstructed from the chat record (not independently re-verifiable from repository prose documents alone, since most of this work's evidence lives in test file content and in your own ability to re-run the suites — which you should do before trusting any of this). ### 3.1 Durable transaction infrastructure (R44.2F family)
A `runDurableTransaction()` helper was added to `utils/db.js`: BEGIN → work (synchronous callback) → COMMIT → atomic same-directory-temp-file-then-rename disk write. On any failure before the rename, memory is restored from a pre-transaction checkpoint and the disk file is untouched. After a successful rename, a parent-directory `fsync` failure is treated as a non-fatal durability *warning* (logged, metered), not a rollback, since the rename itself is the real commit point.

This was wired into: standard LINE order create (`routes/line-orders.js`), LINE shipping create (`routes/line-shipping.js`), popup checkout create (`routes/popup-public.js`), and the shared cancel/void endpoints (`routes/orders.js` — these serve standard, shipping, *and* popup orders through the same two endpoints, branching internally).

**Known NOT durable** (explicitly out of scope, listed in `H1.4.12_R44_2F_MUTATION_INVENTORY.md`): `routes/settings.js`'s `/ga4-realtime` endpoint (still uses the old manual BEGIN/COMMIT/`_save()` pattern), and — the largest remaining category — most POS order creation and other admin CRUD outside the popup-pickup durable paths, which still use the old auto-saving `db.run()`/`_save()` pattern. **Do not assume the whole system is durable.**

### 3.2 Server-authoritative pricing (R44.2D, R44.2G)
Standard LINE and shipping order creation now rebuild canonical item names/prices/subtotal/discount/total from the server's own product data *inside* the durable transaction, ignoring anything the client sends for these fields. A `409 price_changed` is returned if the product price changes between the pre-transaction pricing pass and the in-transaction fresh read (for delivery orders specifically, which need an external delivery-fee API call before `BEGIN`).

`scripts/smoke-h1-4-12-line-pricing-lifecycle.js` is the dedicated suite for this — **last reported 202/202**, including a genuine async-race test that pauses a real `https.request` call (intercepted at the Node `https` module level, not `node-fetch`'s module export, which does not work for this purpose — see that file's own comments for why) to simulate a price change landing mid-request.

### 3.3 Snapshot-based counter restoration (R44.1B family) — the most security-critical part
Every standard/shipping order's counter deduction (quota or preorder slots) is recorded at creation time as a versioned JSON snapshot (`orders.line_counter_allocation_snapshot`, `orders.line_counter_bucket`) — an authoritative record of exactly which products/quantities were deducted, so that cancel/void can restore *exactly* that, regardless of what the product's current (mutable) settings say later.

Two real, confirmed, fixed security bugs (both reproduced with real before/after evidence before any production code was touched, per this project's own strict methodology):
1. A corrupted/mismatched snapshot referencing an unknown or cross-store product used to **silently succeed** (report `ok:true`) while never actually restoring anything — a permanent quota leak. Fixed with an affected-rows check plus (later) a full preflight batch existence check before any `UPDATE` runs.
2. The snapshot's claimed quantity could silently diverge from what was actually in `order.items` (claiming less → permanent partial leak; claiming more → counter driven below true occupancy, an overselling risk). Fixed by adding a read-only `aggregateOrderItemsQty()` cross-validator that must match exactly before any restoration proceeds.

Test suites: `scripts/smoke-h1-4-12-line-counter-snapshot-security.js` (last reported 194/194), `scripts/smoke-h1-4-12-line-counter-snapshot-boundary.js` (client-forgery + response-exposure audit, last reported 73/73), `scripts/smoke-h1-4-12-line-counter-snapshot-migration.js` (cold-start column-migration regression, last reported 8/8).

**A real admin-response field-exposure fix was also made**: `routes/orders.js`'s shared `parseOrder()` serializer used to spread the entire raw DB row (including the two internal snapshot/bucket fields) into every authenticated admin response (detail, list, PATCH, void). A consumer audit found zero real frontend/backend consumers of these fields in any response, so they were excluded via a `delete` loop in `parseOrder()` — a single point of truth covering all four response paths.

This happened at least twice (`smoke-h1-4-12-durable-cart-recovery.js` once, `smoke-h1-4-12-line-pricing-lifecycle.js` once, the latter specifically for a *delivery*-specific cutoff setting — `delivery_business_hours`/`delivery_cutoff_time`/`delivery_today_cutoff_time`/`delivery_today_cutoff_date`, which is a completely separate settings namespace from `takeout_*`). **Links tab** (`public/js/app.js`, search for `ppaRenderLinksTab`, around line 15717):
- `window.ppaLoadLinksTab()` is the entry point; it loads campaigns (if not already cached) and sessions (if not already cached — see the pagination problem in Section 6), then calls `ppaRenderLinksTab()`.

- Unblocked sessions get two URLs via `ppaLinkRow()`: a session-direct URL (`?session=${encodeURIComponent(s.public_code)}`) and a campaign-entry URL (`?campaign=${encodeURIComponent(campaign.public_code)}`) — both using the server-issued `public_code`, never an internal numeric ID.

**Copy**: `ppaCopyText()` uses real `navigator.clipboard.writeText()`.

**Open / Test**: both buttons call `window.open(url, '_blank', 'noopener,noreferrer')`. There is **no confirm dialog** on the Test button — the warning text ("測試下單會建立真實測試訂單...") is just static text printed in the card, not a dialog.

**QR**: `ppaShowQr(url)` uses a **same-origin** vendor library at `/js/qrcode.min.js` — **not** an external CDN (unpkg, jsDelivr, etc.). If `typeof QRCode === 'undefined'`, it dynamically injects a `<script src="/js/qrcode.min.js">`; on that script's `onerror`, it sets `container.textContent` to a Chinese fallback message ("QR Code 產生失敗，請使用複製網址功能"). **This means: to test the QR fallback path, you must block the same-origin `/js/qrcode.min.js` request via Playwright route interception — blocking an external CDN host does nothing, because QR never requests one.**

**Google Maps**: `ppaOpenMap()` builds `https://www.google.com/maps/search/?api=1&query=' + encodeURIComponent(...)`.

**XSS**: a grep for `innerHTML` with string-template concatenation sinks around campaign/location rendering found nothing — rendering appears to go through `.textContent`/`.value` DOM APIs throughout, which is XSS-safe by construction. **This is static evidence only.** No real browser proof of this exists yet — that's exactly what Phase 3C-A's XSS section is supposed to produce, and it's unfinished.

## 6. THE CRITICAL UNRESOLVED PROBLEM: shared fixture pollution / pagination

This is the actual reason the current round is stuck and incomplete. Understand this before touching the file.

**The mechanism**: `GET /api/popup-pickup/sessions` (`routes/popup-pickup.js`, around line 440-471) sorts `ORDER BY pickup_date ASC, sort_order ASC, created_at DESC LIMIT ? OFFSET ?`, and the admin frontend's `ppaLoadJoinSessions()` (`public/js/app.js`, around line 14785) calls it with a hardcoded `limit=100` and **no date filter**, then caches the result in `PPA.joinSessions` behind a `PPA.joinSessionsLoaded` flag that is only reset on a fresh page load (not on tab-switch).

By the time Phase 3C-A's new test block runs — after roughly 300+ prior `BR*`-numbered test cases in the same suite, many of which create their own campaigns/sessions via the same default `pickup_date: taipeiDateStr(2)` — the store has accumulated far more than 100 sessions. Any *newly created* session, even with a carefully chosen `pickup_date`, is not guaranteed to land within the first 100 results of that sorted query. This is a genuine resource-contention problem in the shared test database, **not a production bug** — a real store would never accumulate hundreds of sessions in the time window this matters for, and the 100-row cap is a reasonable UI pagination choice for real usage.

**Approaches tried, in order, and why each was abandoned or is still unresolved:**

1. **Forcing cache invalidation** (`PPA.joinSessionsLoaded = false` before switching tabs) — insufficient alone, since the underlying API call still returns a 100-row page that may not contain the new fixtures.
2. **Choosing an earlier/distinctive `pickup_date`** for the new fixtures to try to sort them to the front of the `ASC` order — insufficient, because by the time this was tried, there were apparently still enough earlier-dated sessions from prior tests to push the new fixtures out.
3. **Direct injection into `window.PPA.joinSessions`** from `page.evaluate()` — **this does not work at all**, because `PPA` is a `const` declared inside the module-scope IIFE in `public/js/app.js` and is **never assigned to `window.PPA`**. `page.evaluate()` runs in the page's global scope and cannot see it. (A stray `if (window.PPA) {}` check in the current file is dead code left over from this failed attempt — see Section 8.)
4. **Playwright route interception on `GET /api/popup-pickup/sessions?limit=100`**, returning a fixed JSON body containing only the intended fixture sessions — this **does** exercise the real `fetch → ppaLoadJoinSessions → PPA.joinSessions → ppaRenderLinksTab → DOM` pipeline, and got the **"published"** and **"draft"** blocked-state test cases passing reliably.
5. **Also intercepting `GET /api/popup-pickup/campaigns`** (same technique, since `ppaShareBlockedReason` for a session that isn't itself blocked falls through to check its **parent campaign's** status, which requires `PPA.campaigns` to contain the right campaign objects) — this was the last thing tried. It did **not** fully resolve the problem: **"paused," "cancelled," and "archived" still failed**, even though:
   - The campaign objects for paused/archived cases were included in the intercepted campaigns response.
   - For "cancelled" specifically — which should need **no** campaign lookup at all, since `ppaShareBlockedReason(s.status, 'session')` checks the session's own status directly — a debug dump of the real PATCH response confirmed the session's `status` field was genuinely `'cancelled'` in the data being fed to the frontend. **This should have worked and didn't, and the reason was never found.**

**Open question, not yet root-caused**: why does "cancelled" (pure session-status, no campaign dependency, confirmed-correct data) still fail to render the blocked message, when "draft" (same mechanism) succeeds? Possible explanations nobody has checked yet:
- Is the route interception actually firing for every attempt, or only sometimes (a `page.route()` timing/race issue)?
- Does `ppaRenderLinksTab()` get called before or after the route-intercepted fetch actually resolves (an ordering bug in the test, not production)?
- Is there some other session-list filtering step between the API response and `ppaRenderLinksTab()` that filters by status before rendering (i.e. maybe `ppaLoadJoinSessions()` or something upstream silently drops cancelled sessions)?
- Is there a difference in how `s.campaign_id` and `PPA.campaigns` entries' `id` field are typed/compared (e.g. one is a string, one isn't) that happens to matter for paused/archived but is a red herring for cancelled?
- Is the test's own card-lookup selector (`cards.find(x => x.textContent.includes(name))`) matching the wrong card, or finding no card because something about rendering order/timing changed?

**This is the actual next step.** See Section 10.
