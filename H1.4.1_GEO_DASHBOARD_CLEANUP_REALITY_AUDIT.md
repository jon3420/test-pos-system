# H1.4.1 Geo Intelligence Dashboard Cleanup — Reality Audit

Baseline: `fix18-10-hotfix30-B5-R5.4-G1.6-GA4-H1.4-MAP-STATE-QA-full.zip` (H1.4 final).
No H1.5 workdir/content used or referenced.

## A. Dashboard map container

- `refreshGeoDashboardKpiBlock()` (public/js/geo-intelligence.js) builds
  `mapContainerId = ${containerId}-map` and calls
  `geoRenderMapBlock(mapContainerId)` (public/js/geo-intelligence-map.js) to
  get the map skeleton HTML (`.geo-map-root` > `#<mapContainerId>.geo-map-canvas`
  + legend/summary/area-list siblings).

## B. Leaflet instance owner

- `geoMapState` in `public/js/geo-intelligence-map.js` (module-level `let`,
  exposed as `window.geoMapState`). `geoInitMap(containerId, rows)` creates
  `geoMapState.instance = L.map(container)` **once** per containerId and
  reuses it on subsequent calls (`if (geoMapState.instance && geoMapState.containerId === containerId) { updateData; return; }`).
  Dashboard and Heatmap tabs share this same instance — confirmed by
  `geo-heatmap-ui.js` (`_geoHeatUiEnsureMapReuse()` reads
  `geoMapState.instance`, never creates a second `L.map()`).

## C. scrollWheelZoom — current state

- **Not configured anywhere.** `grep -rn "scrollWheelZoom" public/js/*.js public/*.html`
  returns no hits in the baseline. Leaflet's default (`scrollWheelZoom: true`)
  applies, which is exactly Problem 1 — mouse wheel over the map always zooms,
  on both tabs, from the moment the map is created in `geoInitMap()`.

## D. Old 8-metric selector (訪客/加購/結帳/完成訂單/營收/成交率/購物車放棄/建議風險)

- Defined as `GEO_EVENT_METRICS` in `public/js/geo-visitor-layer.js`
  (`['visitors','add_to_cart','checkout','orders','revenue','conversion','cart_abandonment','recommendation_risk']`,
  labelled via `GEO_EVENT_METRIC_LABEL`).
- Rendered by `geoVisitorMetricBarHtml(containerId)` (geo-visitor-layer.js),
  wrapped by `geoHeatUiRenderSharedMetricBar(containerId)` (geo-heatmap-ui.js).
- **This bar is rendered once, outside both tab panels** — in
  `refreshGeoDashboardKpiBlock()`'s template: `${heatTabBarHtml} ${mapHtml}
  ${sharedMetricBarHtml} <div id="...-panel-dashboard">...</div> ${heatPanelHtml}`.
  It is visible regardless of `geoHeatUiState.activeTab`, i.e. it shows on the
  Dashboard tab today. This is Problem 3's root cause.
- Clicking a button calls `geoVisitorSetMetric()`, which drives the shared
  choropleth colouring and the Heatmap-only Visitor Summary/Ranking panels
  (`${containerId}-metric-summary`, `${containerId}-visitor-ranking`, inside
  `geoHeatUiRenderVisitorLayerHtml()`, which **is** correctly scoped inside
  `#-panel-heatmap`). Because none of the 13 demo districts currently qualify
  for choropleth colouring (`_GEO_VISITOR_CHOROPLETH_OFFICIAL_CITY_CODES` is
  intentionally empty — see comments in geo-visitor-layer.js), most metrics
  resolve to "no data" text in these summary/ranking panels.

## E/F. "目前沒有符合條件的區域資料" / "暫無資料" renderers

- `_renderGeoTopAreaRows()` / `_renderGeoOrderAreaRows()` (geo-intelligence.js)
  render "目前沒有符合條件的區域資料" for the 高意願/高流量低轉換/外送成交
  Top-3 rows. These belong to `rankingSectionHtml` (排行榜 Top-3 block),
  which is a **different**, older feature from the 8-metric bar / choropleth
  ranking and is **not** in scope for this hotfix (not named in the incident
  report; out-of-scope items per §II/§46). Left untouched.
- The Heatmap-scoped "暫無資料" text (Visitor/Order Summary & Ranking, driven
  by the 8-metric bar) lives entirely inside `#-panel-heatmap` already and is
  fine to keep showing there — the problem is only that the **bar itself**
  (and by extension, encouragement to click it) is visible on the Dashboard
  tab where it doesn't belong.

## G. Geo 訪客/加購/結帳/訂單/成交率/平均外送距離/Geo 辨識率/Unknown 比例 + Geo Quality

- `_geoRenderKpiLiveHtml(vm.overview)` (geo-intelligence.js) renders both the
  8-card `geoBuildKpiSummaryCards()` grid (Geo 訪客/加購/結帳/訂單/成交率/
  平均外送距離/Geo 辨識率/Unknown 比例) and a 5-card legacy-substring
  compatibility block (進站訪客/加入購物車/開始結帳/完成訂單/整體成交率).
  Mounted directly inside `#-panel-dashboard` via
  `<div id="${containerId}-geo-kpi-live">`.
- `renderGeoQualityBlock(vm.quality)` renders the "📡 Geo Quality：
  Good/Degraded/…" line (plus the "目前所有訪客皆為未知區域" warning),
  also mounted directly inside `#-panel-dashboard`.
- Both are **POS Visitor Geo / Acquisition Geo Quality diagnostics** — a
  different data source from the GA4 regional overview markers shown on the
  same map — and both currently render unconditionally on the Dashboard tab.
  This is Problem 2's root cause: GA4 markers show real data while these
  cards can simultaneously show Unknown/Degraded, looking contradictory.

## Are these blocks shared between Dashboard and Heatmap?

- The 8-metric bar (`sharedMetricBarHtml`) — **yes**, shared/visible on both
  (bug).
- The KPI-live cards (`#-geo-kpi-live`) and Geo Quality block — **no**, only
  ever mounted in `#-panel-dashboard`. Heatmap's own Visitor Layer panel
  (`geoHeatUiRenderVisitorLayerHtml`) already has its own independent
  "Geo Event Summary" / "Geo Visitor Summary" / "Visitor Coverage" / "Visitor
  Ranking" mounts (`#-metric-summary`, `#-visitor-summary`, `#-visitor-coverage`,
  `#-visitor-ranking`) fed by the same `geoVisitorState`. These are the
  reuse target for "POS Geo diagnostic detail" per §XI/§XII — no duplicate
  panel needs to be created.

## Decision (Cleanup, not Rebuild)

1. **Scroll wheel** — default-disable in `geoInitMap()` at map creation time;
   add a small, tab-lifecycle-bound interaction state
   (`dashboardMapInteractionState`, new — lives in `geo-heatmap-ui.js`, the
   existing Dashboard⇄Heatmap lifecycle owner) that click-enables on
   Dashboard, always-enables on Heatmap, and resets to disabled every time
   Dashboard becomes active again (activate/deactivate hooks already exist
   in `geoHeatUiSwitchTab()` and in `refreshGeoDashboardKpiBlock()`'s Direct
   Load path).
2. **`sharedMetricBarHtml`** — stop rendering it inside `#-panel-dashboard`'s
   sibling position; render it only inside the Heatmap panel
   (`geoHeatUiRenderPanel()`), where its consumers (`#-metric-summary`,
   `#-visitor-ranking`, `#-summary`, `#-ranking`) already live. No engine
   change, no API change — pure move of one `<div>` from one place in the
   template to another.
3. **`#-geo-kpi-live` + `renderGeoQualityBlock`** — stop rendering inside
   `#-panel-dashboard`; render the same markup inside the Heatmap panel
   instead (new small "Geo 資料品質" mount inside
   `geoHeatUiRenderVisitorLayerHtml()`'s existing column, reusing the exact
   same `_geoRenderKpiLiveHtml`/`renderGeoQualityBlock` functions — no
   duplicate implementation, no new engine).
4. GA4 disclaimer block (`#-dashboard-ga4-label/range/status`) is untouched —
   stays on Dashboard.
5. `decisionCenterHtml`, `emptyStateNotice`, `rankingSectionHtml` (Top-3 +
   ranking table + filter bar), `fulfillmentLine` are **out of scope** and
   left exactly as-is (not named in the incident report; touching them would
   be redesign, not cleanup).

No backend, DB, GA4 query, Range Resolver, Auth, Store Guard, Credential,
Manual Sync API, or Marker Catalog files are touched.

## FINAL FINDINGS (post-implementation, supersedes the "out of scope" note in
item 5 above — see below)

Over the course of implementation, the initial "leave Recommended Actions
and Top-3/ranking untouched" decision was revisited and reversed once the
Final Dashboard Geo DOM Contract was made explicit and unconditional. These
are the findings as actually shipped:

1. **scrollWheelZoom root cause.** Confirmed by `grep -rn "scrollWheelZoom"`
   returning zero hits anywhere in the H1.4 baseline. Leaflet's own default
   (`true`) was silently in effect from the moment `geoInitMap()` first
   called `L.map(container)`. Fixed at the same call site.

2. **Old 8-metric selector root cause.** `geoHeatUiRenderSharedMetricBar()`'s
   output (`sharedMetricBarHtml`) was interpolated into the shared template
   *outside* both `#-panel-dashboard` and `#-panel-heatmap` — visible on
   both tabs regardless of `geoHeatUiState.activeTab`. This is why it showed
   up on Dashboard despite conceptually belonging to Heatmap's choropleth
   controls. Fixed by moving it inside the Heatmap-only diagnostics hook.

3. **POS Geo diagnostics ownership.** `_geoRenderKpiLiveHtml()` (8-card grid
   + 5-card legacy-compat block) and `renderGeoQualityBlock()` were mounted
   unconditionally inside `#-panel-dashboard`, with no tab-awareness at all
   — they always rendered regardless of which tab was active. Moved into the
   Heatmap-only diagnostics hook; functions themselves untouched.

4. **Recommended Actions ownership — moved, not deleted.** `decisionCenterHtml`
   (`geoRenderDecisionCenter(vm)`, reading `vm.recommendation_view_models` /
   `vm.quality_view_models` from the existing `/alerts` response) is a
   legacy geographic recommendation feature, unrelated to GA4. Per the Final
   Dashboard Geo DOM Contract's explicit allowlist (GA4 overview + range +
   map + disclaimer only), it does not qualify to stay on Dashboard. Moved
   into the diagnostics hook. `geoComputeRecommendedActions()` and
   `geoRenderDecisionCenter()` are unmodified.

5. **Top-3 / ranking table ownership — moved, not deleted.** Verified by
   code-dependency inspection (not assumption) that `computeGeoTopAreas()`,
   `_renderGeoAreaRankingTable()`, and `computeGeoAreaRanking()` read only
   the legacy `vm` object built by `loadGeoDashboardData()` — i.e.
   `/api/analytics/geo/funnel`, `/county-summary`, `/alerts` — never
   `geoVisitorState`/`GEO_EVENT_METRICS` (the 8-metric selector) and never
   `vm.overview` (the GA4 persisted data Dashboard is supposed to show). So
   while it doesn't depend on the old selector, it also isn't "an
   independent legitimate GA4 Dashboard summary" — it fails the Contract's
   retention test on that basis and moved to Heatmap alongside the selector
   it has no other natural owner next to.

6. **Production fallback drafted, then explicitly rejected.** An earlier
   iteration added a defensive fallback — if `geo-heatmap-ui.js` wasn't
   loaded (`heatPanelHtml === ''`), diagnostics would render back inline on
   Dashboard, to avoid breaking older standalone tests that `eval` only
   `geo-intelligence.js`. This was correctly identified as a Production
   conditional that violates the "Dashboard clean is unconditional" contract
   (`public/index.html` always loads `geo-heatmap-ui.js` alongside
   `geo-intelligence.js` per the Browser Entry contract — the fallback's
   trigger condition can't occur in real deployment) and was removed.

7. **Legacy standalone tests migrated to the new ownership contract**,
   rather than the fallback being kept to satisfy them. Nine legacy smoke
   suites were updated (assertions changed from "content present on
   Dashboard" to "content absent from Dashboard, present via
   `window.__geoHeatUiDiagnosticsHtml`"); where real DOM interaction was
   needed (Drawer open/close/ESC/focus, ranking expand, a11y, Explorer entry
   points), a manual "Heatmap owner fixture" was mounted in the *test* only
   (`document.body.innerHTML += <div>${window.__geoHeatUiDiagnosticsHtml}</div>`)
   to simulate what `geoHeatUiRenderPanel()` does in Production — this
   fixture pattern is confined to legacy test files and was never used as
   evidence of real Production ownership (that was verified separately, with
   real `geoHeatUiRenderPanel()`/`geoHeatUiSwitchTab()` calls, in the H1.4.1
   Target Runtime).

8. **Duplicate ranking ID — a real Production DOM integration bug**, found
   by the Target Runtime, not a test-authoring mistake. The legacy Top-3
   ranking table (`geo-intelligence.js`) and the Heatmap Engine's own,
   unrelated Order/Visitor ranking list (`geo-heatmap-ui.js` /
   `_geoHeatUiBindRankingEvents()`) both used the literal id
   `${containerId}-ranking`. This collision existed in principle before
   H1.4.1 too, but never manifested because the two features lived in
   different, non-simultaneously-visible places; H1.4.1 made it real by
   moving the legacy table into the same Heatmap panel where the Engine's
   ranking list already lived. Fixed by renaming the legacy table's id to
   `${containerId}-legacy-ranking` (2 call sites). Classified **REAL
   PRODUCTION DOM INTEGRATION BUG**, not test-only — it is listed in the
   Production Diff for `geo-intelligence.js`.

9. **No second map.** `geoMapState.instance` remains the single shared
   Leaflet instance across Dashboard and Heatmap for the entire lifetime of
   a page load, confirmed by the Target Runtime (`counters.mapInstances ===
   1` after 20 Dashboard↔Heatmap round trips plus multiple explicit
   refreshes).

10. **Backend frozen.** `diff -rq` against a freshly re-extracted H1.4
    baseline shows zero differences in `services/`, `routes/`, `utils/`,
    `middleware/`, `public/index.html`, and `public/css/`.
    `services/ga4GeoSyncService.js` SHA256 is byte-identical on both sides.

11. **H1 Range unchanged.** `geo-range-resolver.js` and
    `geo-range-control.js` were not touched this round; all ten range modes
    (today/yesterday/single/7d/30d/90d/180d/this_year/last_year/custom)
    remain intact end-to-end (verified by the unchanged H1 Range Integration
    Runtime, 35/35, and by Target Runtime Category E).

12. **SHA256 freeze-test updates are Test-only.** Three smoke tests
    (`a1-1`, `a1-2`, `a2-geo-event-engine`) each independently freeze-check
    `geo-intelligence-map.js` against a byte-for-byte baseline hash. Since
    this file's `scrollWheelZoom`/wheel-hint change is an intentional,
    documented Production change this round, all three expectations were
    updated to the same real post-change SHA256
    (`9997c0b84a867e27b11a1a499b06de0b83f78403dd9feba401a6edbc49f1970d`,
    verified 64 characters, verified identical across all three files,
    verified equal to the file's actual computed hash). This is a Test-only
    diff — the Production Diff entry is the file change itself, not these
    three test expectation updates.
