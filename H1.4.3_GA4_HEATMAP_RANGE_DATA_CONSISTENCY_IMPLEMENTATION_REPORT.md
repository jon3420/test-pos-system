## 5. Cross-range Cache Defect (the actual fix)

**Defect:** `lastGoodPayload` was cached on every successful fetch with no
record of which range it belonged to. On any subsequent fetch *failure*
(for any range), the code unconditionally reused that cached payload,
tagging it `stale: true` but still rendering it as the current view's
data — regardless of whether the currently-selected range was the same one
that produced the cache.

**User-visible effect:** if range B's fetch failed shortly after range A
loaded successfully, the screen kept showing range A's Map markers, Table
rows, and status — which looks exactly like "the range buttons don't do
anything."

**Fix (§6, Range Identity Fix):** added `lastGoodRangeKey` next to
`lastGoodPayload`, and a pure helper `_geoGa4H1FetchRangeKey(mode, opts)`
that builds an identity string from the transport mode **and** the actual
`startDate`/`endDate` — not `mode` alone, because `90d`/`180d`/
`this_year`/`last_year`/`single`/`custom` all transport as
`apiRange==='custom'` and would otherwise collide. Fallback is now gated:
`geoGa4H1State.lastGoodRangeKey === currentRangeKey`.

- Same-range failure → last-good cache for *that same range* may still be
  shown (graceful degradation, unchanged behavior for this case).
- Cross-range failure → cache is not reused; a clean empty/error state is
  rendered instead.

Verified by Heatmap Range Runtime Parts D and G (64/64 total, including
this fix specifically), and static audit Category E/F (part of 161/161).

## 6. Range Identity Fix — detail

See §5. No change was needed to the resolver or the backend — both were
already computing/reading the correct actual `start`/`end` dates. The fix
is entirely in how the *frontend cache* keys itself.

## 7. Overseas/Other Display Collision

**Defect:** `_geoGa4H1RowLabel()` rendered every row with
`normalization_status ∈ {unknown, overseas_or_other, ambiguous}` as a
fixed literal string ("Unknown" / "Overseas／Other" / "Ambiguous"),
regardless of the row's actual raw identity. Two persisted rows for two
genuinely different unresolved locations (e.g. Japan vs. United States)
were indistinguishable in the Table.

**Root cause classification:** display-identity collision, **not**
persisted-identity collision — `raw_location_key` (built from
country+region+city) already differed between the two rows; they were
never the same underlying data.

**Fix:** `_geoGa4H1RawContextSuffix(r)` appends available raw
`country_raw`/`region_raw`/`city_raw` to the label. `raw_location_key` is
untouched. No `activeUsers` summation was introduced anywhere — rows
remain separate; only their *label* changed.

**Not classified as fixed.** Automated same-range testing shows no
pipeline defect under a controlled, fully-known snapshot. The original

`synced_at`/range identity for the Heatmap table at that moment, so the

candidate-cause list (A–E) — none has been selected as *the* root cause.
Manual re-verification with all three surfaces on the identical date range
is required (see Reconciliation Report Part B and Manual QA doc).
