## What "real browser QA" means here, precisely

`scripts/smoke-h1-4-12-popup-real-browser.js` launches a real Chromium binary via
Playwright (already provisioned in this environment at `/opt/pw-browsers`, not added to
`package.json` — production dependencies are untouched) against a real Express server
and a real ephemeral sql.js database. It exercises real page navigation (including a
genuine full-page reload when `_popupNavigateTo()`'s production path —
`window.location.replace()` — fires), real `sessionStorage`/`localStorage`, real
viewport rendering across 320/360/390/430/768/1280px, real tap/click interaction, and
real horizontal-overflow measurement (`scrollWidth <= clientWidth`). This is explicitly
not jsdom, and this document does not claim jsdom results as real-browser evidence
anywhere.

What it does **not** cover: the real LIFF SDK, a real LINE login screen, or a real call
to LINE's servers — those require LINE Developers Console access and are tracked in the
Manual Acceptance checklist, not claimed as verified here.

## Fault-injection and atomicity evidence (backend)

- `commitPopupRestore()`: a test patches the DB's `run()` to throw mid-transaction
  between the receipt-consume and token-consume statements. Result: the function returns
  a clean failure (no uncaught throw), the token remains `opened`, the receipt remains
  `prepared`, and a subsequent unmodified retry with the same receipt succeeds and
  correctly transitions both to `consumed`.
- `preparePopupRestore()`'s receipt-supersede step: same fault-injection pattern between
  the supersede `UPDATE` and the new-receipt `INSERT` — the original receipt survives
  unmodified and remains committable.
- `initDb()`'s partial-unique-index migration: verified via genuinely separate `node`
  subprocesses (not same-process calls, which would hit the `wrappedDb` singleton cache
  and produce a false pass) — a DB file with pre-existing duplicate `status='prepared'`
  rows causes a fresh cold start to `throw`/exit non-zero, without deleting or
  auto-selecting either conflicting row.

## Rate limiting

## RC2 — Security Corrective Audit (this update)

Five backend security gaps found in RC1 review, fixed:

1. **IP trust model.** `clientIp()` in three route files previously read
   `req.headers['x-forwarded-for']` directly and unconditionally — meaning any client
   could forge that header to get a fresh rate-limit bucket per request. Fixed: all
   limiters now key exclusively on Express's own `req.ip`, which already respects
   `server.js`'s existing `app.set('trust proxy', computeTrustProxySetting(...))`. With
   `TRUST_PROXY` unset/false (the default), forged `X-Forwarded-For` values — including
   empty, comma-separated multi-value, IPv6, and non-IP strings — have zero effect on
   the rate-limit key; verified with 35 requests using 35 different forged headers still
   getting limited at the same real threshold. When `trust proxy` is deliberately
   enabled, `req.ip` correctly varies per the proxy chain, verified directly. Limiter
   logic was extracted into `utils/rateLimiter.js`, shared by all five endpoints, with a
   periodic bucket sweep and a hard cap (default 5000, tested independently at 100) so
   an attacker rotating many fake source values cannot grow the Map unboundedly. `429`
   responses never change token/receipt state and use the exact same response body as
   any other failure — verified with a real (not forged-IP) valid token hitting an
   exhausted quota.
2. **Popup empty-snapshot contract, tightened.** `validatePopupRestoreSnapshot()` now
   rejects a raw `items: []` snapshot as `invalid_snapshot` outright — previously an
   empty array passed structural validation and could reach reconciliation, producing
   ambiguity with a legitimately-emptied cart. `createRecoveryResumeToken()` now also
   rejects, at creation time, a `popup_order` token with no cart items or with items
   that would be silently filtered away by the pre-existing loose `Number()` coercion —
   closing off the path where a "successfully created" token secretly carried an empty
   snapshot. The standard `line_order`/`line_shipping` recovery token creation path is
   untouched and still permits empty carts, exactly as before.
3. **`liff-config` fresh authority.** Previously accepted any of the three page types
   and never re-checked store/license/feature/session state — it only checked the
   token's own status machine. Now restricted to `page_type==='popup_order'` and reuses
   the same `_resolvePopupSessionForToken()` SSOT as the other popup endpoints (store
   active, license active, `line_order` feature, `popup_pickup_enabled`, session and
   campaign not draft). The code collapses all of these failure modes — inactive store,
   inactive license, disabled feature, disabled popup flag, draft session, draft campaign,
   nonexistent session, and a standard-page-type token — to the same non-enumerable
   response. **Correction (RC2.1): the RC2 test suite did not exercise all eight of those
   modes.** It exercised six on the `liff-config` path, one of them under the wrong name, and
   never tested an inactive store (`stores.active=0`). See "RC2.1 — 1. Correction of RC2
   coverage claims" below for the exact list.
4. **`resolve-target` error contract, unified.** Previously returned the internal
   `result.reason` directly (`not_found`/`expired`/`uid_mismatch`/`consumed`/...) despite
   a comment claiming non-enumerability — an actual signal leak. Now every failure,
   regardless of cause, returns the exact same `{success:false, reason:'resolve_failed'}`
   body at the same HTTP status; verified by comparing serialized JSON across three
   genuinely different failure causes (nonexistent token, consumed token, wrong
   identity) and confirming byte-for-byte identity. Also gained its own rate limiter
   (previously had none).
5. **Commit transaction, hardened.** `commitPopupRestore()`'s two conditional `UPDATE`
   statements now each check `db._db.getRowsModified() === 1` immediately after
   execution; anything else (0 rows — status already changed by another path; more than
   1 — should be structurally impossible, checked defensively anyway) throws inside the
   transaction, triggering the existing rollback path, with `_save()` never reached.
   Verified against a receipt whose status was mutated to `superseded` between prepare
   and commit, and a token mutated to `consumed` by a separate path between prepare and
   commit — both correctly rejected rather than silently succeeding.

New suite: `scripts/smoke-h1-4-12-popup-recovery-rc2-security.js`, **21/21 × 3 TZ** as

### 2. What RC2.1 changed in `smoke-h1-4-12-popup-recovery-rc2-security.js` (21 → 78 assertions)

- The old `store-inactive` case is renamed **`license-inactive`**; a real
  **`store-inactive`** (`stores.active=0`) is added.
- **Store-table column note.** `stores.id` is `INTEGER PRIMARY KEY AUTOINCREMENT`; the string
  store code (`'store_001'`) lives in `stores.store_id`. The injection is therefore
  `UPDATE stores SET active=0 WHERE store_id='store_001'`. The variant
  `WHERE id='store_001'` matches **0 rows** (measured: `getRowsModified()===0`) — a silent
  no-op. To make a vacuous injection impossible, every injection now goes through
  `injectSql()`, which throws unless exactly one row was modified (verified: with the
  `WHERE id=` variant substituted in, the suite aborts with a fatal error instead of passing).
- Every injection case runs in a fixed order: **token creation → positive control (same
  token must succeed with a `liff_id`) → injection → `liff-config`**. The injection always
  happens after the token exists and before `liff-config` is called.
- Original values are **read from the database immediately before injection** (whole-row
  snapshot) — no seeded default is assumed. A `finally` block restores from those captured
  values, then asserts the monitored state is byte-identical to the snapshot. The
  hard-coded restores of RC2 (`active=1`, the file-level `features` constant, `'1'`) are gone.
- Every rejection case asserts: HTTP 404, `{success:false, reason:'liff_config_unavailable'}`,
  a body byte-identical to the "non-existent token" body, and that the token's **entire row**
  is unchanged. In addition, five fields are compared one by one and named in the failure
  detail: `status` (must still be `bound`), `opened_at` and `consumed_at` (must still be
  empty), `expires_at` (must be non-empty and unchanged) and `popup_session_public_code`
  (unchanged and still bound to the original session code).
- **Final RC2.1 case, `session-deleted`:** valid session and `popup_order` token are created,
  `liff-config` is called and must return 200, then the session is removed through the
  official `DELETE /api/popup-pickup/sessions/:id` API (the session has no orders or
  allocations, so the API allows it). `liff-config` must then return the unified 404 with a
  body byte-identical to the non-existent-token body, and the token row must be unchanged.
  `finally` restores the session by re-inserting the exact pre-injection row (and its
  `popup_session_products` rows) — each `INSERT` is checked for `getRowsModified()===1` —
  asserts the rows are byte-identical to the snapshot, and then calls `liff-config` once more:
  it must succeed again, proving the restore really made the session usable and left no
  fixture residue. No direct-SQL injection is used for the deletion itself.
- **Timing of `session-draft` and `campaign-draft`.** Both already followed the required
  order and were not duplicated: fresh session and token → positive-control `liff-config`
  = 200 → *after token creation*, official PATCH API sets the session (resp. its parent
  campaign) to `draft` → `liff-config` = unified 404 → token row unchanged → `finally`
  restores the captured status through the API and verifies it. `campaign-draft` is therefore
  the parent-campaign counterpart of `session-draft`; no further symmetric case was needed.

**Section 6b — fresh-read evidence, enabled → disabled → enabled (23 assertions)**

`middleware/featureGate.js#getStoreLicense()` keeps a 30-second per-store cache of
`licenses.active` and `licenses.features`. The test deliberately makes that cache stale in
both directions and checks `liff-config` follows the database, not the cache. It does this
through behaviour, not code inspection.

| Phase | Database | featureGate cache (read directly via `getStoreLicense`) | `liff-config` must |
|---|---|---|---|
| E1 | enabled | primed → enabled | 200 + `liff_id` |
| D | **disabled** (cache not invalidated) | still **enabled** — asserted, proving the cache is live and would have wrongly allowed | unified 404 |
| E2 | re-enabled (cache not invalidated) | primed to **disabled** while DB was disabled, still **disabled** after DB re-enabled — asserted | 200 + `liff_id` |

D proves no wrongful allow from a stale cache; E2 proves no wrongful rejection from a stale
cache. Dimensions: `license-active` (9 assertions), `line-order-feature` (9),
`store-active` (5 — `featureGate` does not read `stores.active` at all, so no cache
assertions apply; the same E1→D→E2 sequence proves it is read live). Each dimension also
asserts the token row unchanged across the three calls and exact restore with the cache
cleared afterwards. The whole suite runs in ~2.5 s, far inside the 30 s TTL, so the
stale-cache assertions are not at risk of a TTL boundary flake.
