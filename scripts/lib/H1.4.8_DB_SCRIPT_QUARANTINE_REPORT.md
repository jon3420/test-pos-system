## 2. Non-exclusive reachability metrics vs. the mutually-exclusive safety classification

These are **different dimensions** and must not be added together:

| Metric | Definition | Count |
|---|---|---|
| `utilsDbReachableCount` | Directly or indirectly (via routes/services/middleware) requires `utils/db`, OR spawns `server.js` (which itself calls `initDb()` unconditionally at its own top level) | 71 |
| `realPathDeleteCount` | Calls `unlinkSync`/`rmSync` on a variable that resolves to the real `data/pos.db`, **regardless of whether the file also requires `utils/db`** | 56 |
| `spawnServerCount` | Spawns `server.js` as a subprocess | 9 |
| **`safetyClassification`** | **Final, mutually exclusive, covers all 186** | **186** |

The overlap: all 17 `run-regression-*.js` orchestrators fall inside `realPathDeleteCount` (56) but
**none** of them are inside `utilsDbReachableCount` (71) — they never require `utils/db`
themselves, they only `execFileSync` child *processes* and separately `unlinkSync` the real DB
file directly. This is exactly why a naive "DB-touching = 71" scan missed them entirely last
turn. Safety classification correctly folds both metrics (plus DROP/INSERT/UPDATE/initDb signals)
into one mutually-exclusive bucket per file.

**Manual review of the surrounding text at each citation found no imperative/mandatory-gate

This is a real, load-bearing finding, not a shortfall: it means there is currently **no proven

information for Stage 3 planning — it means P1 (documented-but-not-gated) is where the real risk
concentration is, not a hidden P0.

## 6. Fixed-point closure of the 4 (now-P1) regression roots

mechanisms, confirmed via direct source reading:
- Literal `SUITE` tuple entries: `['scripts/....js', pass, total, 'label']`
- `new Function(codeUpToSuiteMarker, ...)` execution of an **earlier** orchestrator's top-level
  code up to (and including) its own `SUITE` assembly line — confirmed via source that in every
  case checked, the destructive `unlinkSync(DB_FILE)` call in the inherited file sits **after**
  its `SUITE` marker line, so this specific execution path does not itself trigger a delete (still
