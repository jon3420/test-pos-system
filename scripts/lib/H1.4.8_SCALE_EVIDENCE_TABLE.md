# H1.4.8 — D3 / D53 / D1200 / E1 / E40 Scale Evidence Table (Stage 1 deliverable, CORRECTED)

**This revision replaces an earlier version that contained a real bug.** The original
`maxBindFingerprint`/`maxBindPhase` fields in `scripts/run-h1-4-8-scale-child.js` were computed
with a single-winner `reduce` (`s.bindCount > best.bindCount`), which returns only the *first*
SQL statement encountered with the maximum bind count and silently discards every other query
tied at the same maximum. The first Markdown version of this table trusted that single-winner
field and reported "route-wide max bind is never the identity query," which is **true for
D3/E1/E40 but false for D53/D1200**, where the direct-member identity query is one of six queries
tied at the max. This was a genuine data-collection gap, not a logic conclusion — fixed below.

## 0. Fix applied

`scripts/run-h1-4-8-scale-child.js` (test-only script, no production code touched) now also
computes `coMaxSources[]`: every SQL execution whose `bindCount === maxBindCount`, grouped by
`(phase, exact fingerprint)` so that same-shape-different-phase queries are never merged and
same-fingerprint-repeated-execution queries are counted correctly. Two new assertions were added
and are included in every case's pass count below:

- **ENGINE2** — every entry in `coMaxSources[]` has `totalBindCount === maxBindCount` (no stale
  or mismatched entries).
- **ENGINE3** — the sum of `executionCount` across `coMaxSources[]` equals the actual count of
  `sqlLog` entries with `bindCount === maxBindCount` (no co-max source silently dropped).

All 5 cases re-run after the fix: **21/21 PASS** (19 original + ENGINE2 + ENGINE3). Full
`run-h1-4-8-product-funnel-semantics-runtime.js`: **338/338 PASS**, unaffected. `data/pos.db`
SHA-256/git-hash-object/size/**mtime** identical before and after this entire re-run batch (mtime
unchanged confirms zero writes, not just zero net diff), no WAL/SHM/journal, no tmp residue.

Engine constants (parsed from `PRAGMA compile_options`, not hardcoded):
`MAX_VARIABLE_NUMBER = 32766`, SQLite `3.49.1`.

tie is a fixture property, not a code coupling — but the identity query is unambiguously one of
the six, not excluded.

## 3. Corrected summary wording

D3/E1/E40's route-wide max bind (51) comes from a single fixed-size geo-intelligence CTE that is
completely unrelated to visitor or product count and does not include the identity query.
D53/D1200's route-wide max bind (54 / 1201) is shared by 6 queries, including 5 cart-id lookups
in the cart-analysis path and the direct-member identity query itself — all six tied because this
fixture happens to produce exactly one cart per visitor. The route-wide max cannot be attributed
to any single source in D53/D1200, and it is factually incorrect to say identity never reaches the
max — it does, in exactly those two cases, tied with five other queries.
