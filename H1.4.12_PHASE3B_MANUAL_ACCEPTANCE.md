# H1.4.12 Phase 3B — Manual Acceptance Checklist

This document tracks the items that automated testing (jsdom + real Playwright/Chromium
browser QA) explicitly **cannot** verify, because they require either a real LINE
Developers Console configuration or a real physical device with the LINE app installed.
No automated test result substitutes for these. Nothing here may be checked off by
an automated process — every `[x]` must carry a real date, environment, verifier name,
and evidence reference.

**Status of this document: all items pending. Phase 3B is not approved for production
until every item below is verified by a human.**

---

## A. LINE Developers Console (requires a human with Console access)

- [ ] Pending — `line_popup_liff_id` setting exists and is populated for the pilot store.
- [ ] Pending — The LIFF app referenced by `line_popup_liff_id` is enabled (not disabled/archived) in the LINE Developers Console.
- [ ] Pending — The LIFF app's Endpoint URL origin matches this deployment's real production origin.
- [ ] Pending — The LIFF app's Endpoint URL path actually allows landing at `/popup-order` (not just the origin — the specific path routing).
- [ ] Pending — The LIFF app's requested scopes include whatever is actually needed for `liff.getIDToken()` to succeed (`openid` at minimum).
- [ ] Pending — The LINE Login Channel ID configured for the LIFF app matches the store's `line_member_login_channel_id` setting used by `utils/lineMemberAuth.js`'s `verifyLineIdToken()` audience check.
- [ ] Pending — A real LINE test account can complete `liff.init({liffId})` without error inside the LIFF app context.
- [ ] Pending — When not already logged in, `liff.login()` correctly returns the user to the original recovery landing URL (not a generic page) after LINE login completes.
- [ ] Pending — The ID token's `aud` claim, when checked against LINE's real `/oauth2/v2.1/verify` endpoint (not a fixture), matches the expected channel ID for a real end-to-end call (this repo's `smoke-h1-4-12-popup-recovery-bootstrap.js` stubs only the network transport to LINE's endpoint — it does not call the real LINE API).
- [ ] Pending — A real LINE in-app browser session can complete the full landing → bootstrap → resolve-target → handoff → verified recovery entry chain end to end.
- [ ] Pending — Confirmed the flow does **not** depend on the `line_member_liff_id` fallback for the popup recovery landing in production (i.e., `line_popup_liff_id` is actually set, and the fallback path — which this codebase deliberately does not assume is Endpoint-URL-compatible — is never exercised in the approved configuration).

## B. Real devices (requires physical hardware, not emulation)

- [ ] Pending — iPhone Safari: ordinary `/popup-order?session=...` renders correctly, no horizontal scroll, all controls reachable.
- [ ] Pending — iPhone, LINE in-app browser: same as above, plus a full recovery landing → restore flow.
- [ ] Pending — Android Chrome: ordinary popup entry and full recovery flow.
- [ ] Pending — Android, LINE in-app browser: full recovery flow (this is the actual real-world entry point for the recovery push notification).
- [ ] Pending — A real Android device with an approximately-360px-wide screen (not just a Chromium viewport emulation) confirmed visually free of horizontal overflow and with all tap targets reachable.
- [ ] Pending — On-screen keyboard appearing for the customer name/phone form fields does not obscure the submit button or make it unreachable.
- [ ] Pending — Pressing the device Back button, or pulling to refresh, after a completed or in-progress recovery does not re-trigger or duplicate a restore.
- [ ] Pending — A network interruption during `commit-popup-restore` (e.g., airplane mode toggled mid-request on a real device) followed by reconnecting and retrying behaves as designed (same-receipt retry, no duplicate order/cart state).
- [ ] Pending — Confirmed no recovery token, member session value, or receipt is visible in: the address bar after landing completes, the browser's shareable link/copy-link affordance, or the browser's visible history/tab-switcher preview on a real device.

- Real Chromium via Playwright (`scripts/smoke-h1-4-12-popup-real-browser.js`, 36/36 assertions): real navigation, real `sessionStorage`/`localStorage`, real viewport rendering at 320/360/390/430/768/1280px, real click/tap interaction, real horizontal-overflow measurement, real XSS-inertness in an actual DOM, real URL scrub timing across an actual page reload.

That gap is exactly Section A above.
