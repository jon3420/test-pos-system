## 一、一般點餐首屏被會員 Gate 擋住

### 在 C3.1 重現

測試設定 LIFF ID 與「結帳前會員」模式，並由測試攔截 LIFF SDK 的下載、讓它一直不回應。結果：

- SDK 確實被請求 1 次；
- 17 張商品卡已經建好；
- 但 `#content` 仍是 `display:none`、`#loading` 仍是 `block`，顧客只看到「載入中」。

本輪新增測試的 F 段在 C3.1 的結果：**8 通過／8 失敗**。

### 根因

- C3.1 修正 `_memberGateInitPromise` 的作用域之後，`restoreCart → await 會員 Gate → 顯示 content` 這個順序開始真正執行。
- 會員 Gate 的等待鏈包含：下載 LIFF SDK、`liff.init`、被動辨識、好友狀態、Handoff 還原等網路操作。
- 任何一段卡住，一般瀏覽的顧客就看不到商品頁。

### 修正（`public/line-order.html` 的 `init()`）

**1. 一般瀏覽不再等會員 Gate**

只要店家、商品、日期時段、付款方式與既有的 `restoreCart()` 都完成，就立即顯示商品頁。

會員 Gate 繼續在背景執行。進站、好友、結帳驗證等規則照舊，由 Gate 本身與送單流程負責：

- 進站登入、好友 Gate 會在 LIFF 就緒後顯示；
- 結帳前會員、好友要求在送單時檢查。

這與 C3 以前正式上線時的實際行為相同（當時程式碼雖然寫了 await，但因為作用域錯誤從來沒有等過）。

**2. 需要身分驗證的還原：鎖住，完整等待，只執行一次**

適用於本頁網址帶有 `recovery_token`（LINE 提醒訊息的 Recovery）或 `cart_token`（Messenger→LINE 的 Handoff）的情況。

- **一進頁就鎖住**：購物車異動（加入、增減、移除、清空、再購）與送單都會被擋下，頁首顯示「正在確認 LINE 會員身分並還原你的購物車…」。顧客仍可以瀏覽商品。
- **完整等待後才還原**：背景流程會**完整等待** `_memberGateInitPromise`，之後才觸發 Recovery bootstrap。順序維持 H1.4.10 Phase 4B 的設計：restoreCart → 會員 Gate → Recovery。Handoff 本來就在 Gate 內部執行。整個頁面只執行一次。
- **完成或失敗後才解鎖**：例如驗證被拒時，會顯示既有的「無法驗證 LINE 會員身分」提示。
- **不用計時器假裝成功**：鎖住 6 秒後，畫面才出現「先繼續點餐（不等待還原）」按鈕，必須由顧客**明確點選**才會解鎖。系統不會自動放行，也不會假裝驗證成功。
- **不覆蓋本頁的購物車**：顧客選擇先繼續點餐、並且在本頁調整過購物車之後，如果還原才完成，Recovery／Handoff **不會覆蓋**購物車，只會提示「為避免覆蓋，未套用…的購物車內容」。這個檢查由 `_restoreMayOverwriteCart()` 負責，在寫入購物車前執行。

**3. 想買登記的登入導回**

- `_initProductDemand()` 同樣完整等待同一個 Gate Promise，等完才恢復表單。
- 待恢復紀錄只在三種情況才消耗：成功重開、使用者明確關閉、逾時。
- C3.2 再補一個情況：導回時商品已不符合新增登記的條件（例如已恢復販售），這時**不消耗**紀錄、本頁不再重試，並提示顧客。
- 之前在 C3.1 是先消耗、再嘗試開啟；開不起來時紀錄就這樣不見了。

### 原本的靜態測試

`run-h1-4-10-phase4b-recovery-frontend-targeted.js` 的 Bootstrap-B 斷言是「原始碼包含 `await _memberGateInitPromise` 與 `handleRecoveryResumeFromUrl()`」。

- C3.2 的背景流程仍然是 `await _memberGateInitPromise` 之後才 `await handleRecoveryResumeFromUrl()`，所以這條斷言**原封不動通過**，沒有修改或放寬。
- 另外新增的 F6／F7／F8 以真實瀏覽器驗證了實際執行順序：身分未確認前不呼叫還原 API、不送單、不覆蓋購物車；Gate 完成後只還原一次。

## 二、商品 ID 互換時，重新對應撞到有效登記唯一索引

### 在 C3.1 重現

- 目前店裡：招牌飯＝801、對照湯＝701，同一會員兩款都有有效登記。
- 舊完整備份（沒有想買登記分類）：招牌飯＝701、對照湯＝801。
- 結果：預覽即失敗；三款商品循環也失敗；最終衝突的情況，也沒有用明確的原因回報。

本輪新增測試的 X 段在 C3.1 的結果：**4 通過／11 失敗**。

### 根因

`remapPreservedDemand()` 是逐筆把 `product_id` 直接改成新值。互換時，第一筆就撞到 active 部分唯一索引 `(store_id, product_id, line_user_id)`，導致整批回滾。

### 修正（`utils/migrationV2.js`）

1. **先做最終衝突檢查**：在任何更新之前，依對應結果推算最終狀態。如果同一會員對同一個新商品會有兩筆有效登記，就以 `DEMAND_PRODUCT_REMAP_FAILED`（`reason: final_conflict`）拒絕並回滾。
2. **分兩階段更新**：
   - 先把要變動的列改成「每列唯一的負數暫存值」（`-資料列 id`）；
   - 再改成最終商品 ID；
   - 完成後核對，不得殘留任何暫存值。
3. **其他保證不變**：
   - 支援互換與任意循環。
   - 唯一索引全程保留、沒有停用。
   - 會員、份數、偏好、週期、期限、狀態、同意關聯都不動。
   - 全部在同一個交易內，預覽與正式匯入共用同一段程式。
   - 不呼叫任何通知。

詳見 `03_BACKUP_RESTORE_DEMAND.md`。

## 五、行為說明

1. **首屏**：一般瀏覽不再等會員 Gate。若店家設定「進站必須登入」或「必須加好友」，商品頁會先出現，Gate 在 LIFF 就緒後才蓋上。這是 C3 以前正式上線時的實際行為；C3.1 曾短暫改成等 Gate 完成才顯示，C3.2 回到原本行為。
2. **Recovery／Handoff 連結**：購物車與送單會鎖到身分確認完成。顧客可以在 6 秒後自行選擇「先繼續點餐」；選了之後，稍後完成的還原不會覆蓋顧客在本頁調整過的購物車。
3. **舊備份完整取代**：支援商品 ID 互換與循環。只有「無法唯一對應」或「會產生重複有效登記」時才拒絕。

## 六、LINE 真機最短驗收

請在 LINE App 內開啟測試店的 LIFF 點餐頁，店家設定使用正式的 LIFF ID：

1. **一般進站**：首屏應在商品資料載入後立刻出現，不要停在「載入中」。可以加入購物車、開啟購物車。
2. **結帳前會員**（`checkout` 模式）：未登入時按「確認下單」，會出現登入；登入導回後購物車還在，只要再按一次送出。
3. **Recovery**：從 LINE 提醒訊息開啟還原連結。頁首先顯示「正在確認 LINE 會員身分…」，期間無法調整購物車或送出；完成後購物車還原、提示消失。確認只有 1 筆還原、沒有自動送單。
4. **Handoff**：從 Messenger「到 LINE 完成結帳」開啟。同上，完成後直接進入結帳，購物車內容正確，只還原一次。
5. **想買登記**：未登入時對暫停販售商品按「我想買」→「以 LINE 登入」，導回後表單只自動開啟一次；重新整理不再開啟。
6. **進站必須登入／必須加好友**（若店家有使用）：確認 Gate 仍會出現且不可略過（不可略過的模式），商品頁先出現屬預期。
7. **（可選）網路不佳**：開啟手機的弱網路模式再做第 1 點，確認首屏仍可瀏覽。
