# R54.4／MBV2-HF1-C3.2：想買登記的備份與還原說明（更新版）

> 本文件取代 C3.1 `03_BACKUP_RESTORE_DEMAND.md`（C3.2 修正第三節的商品 ID 互換／循環，並新增「最終衝突」拒絕條件）。
> 原本取代的是 C3 `03_DEMAND_SCHEMA_AND_MBV2.md` 第四節「MBV2 備份與匯入」。
> 資料表欄位、遷移方式、設定值與 C3 相同，沒有變動，請直接參考 C3 文件第一～三節。

## 一、分類

MBV2 有一個分類 `product_demand`，顯示名稱「商品想買登記」，包含兩張表：

- `product_demand_requests`（想買登記）
- `product_demand_consents`（補貨通知同意）

完整備份一定會包含它；選擇性備份可以自己勾選。分類總數是 13 個。

## 二、各種匯入情境

| 備份檔 | 匯入模式 | 對想買登記／同意的處理 |
|---|---|---|
| 含 `product_demand` | 合併／略過 | 用 `request_uuid`／`consent_uuid` 判斷是否同一筆，不會重複新增。商品依對照表、名稱快照對回目標店。目標店已有「同一會員＋同一商品」的有效登記時，保留現有那筆 |
| 含 `product_demand` | 完整取代 | 清除後以備份為準，商品與登記一起重建，關聯一致 |
| **不含** `product_demand`（C2 或更早的舊備份），且有選「商品資料」 | 完整取代 | **C3.1 修正**：保留現有的登記與同意，並且**重新對應到重建後的商品**（見第三節）。無法唯一對應時，整次拒絕 |
| 不含 `product_demand`，也沒選「商品資料」 | 完整取代 | 商品不會被重建，登記與同意保持不變 |

## 三、舊備份完整取代：商品關聯怎麼重新對應（C3.1 建立，C3.2 修正）

### C3 的問題

- 完整取代會清除商品，再用備份檔裡的商品 ID 重新建立。
- 舊備份沒有想買登記分類，所以登記與同意會被保留，但仍指向**舊的商品 ID**。
- 結果有兩種錯誤：
  - **孤兒資料**：例如登記指向 801，但商品已變成 701。
  - **指錯商品**：備份裡的 801 是另一款商品，登記就被算到那款商品上。
- 後台統計因此歸零或算錯，而匯入卻回報成功。

### 作法（C3.1 起；C3.2 新增第 4 點、修正第 5 點）

這套作法寫在 `utils/migrationV2.js` 的 `snapshotPreservedDemand()`／`remapPreservedDemand()`。整個過程在同一個交易內完成，**預覽與正式匯入走同一段程式**；預覽最後會回滾。

1. **清除商品之前**，記下每個被登記或同意引用的商品的識別資料：
   - 目前商品的條碼（非空白時）；
   - 目前商品的名稱；
   - 商品已經不存在時，改用登記上的商品名稱快照。
2. **商品依備份重建之後**，在目標店的新商品裡找對應，**不依賴數字 ID 是否相同**：
   - 條碼恰好 1 筆相符 → 採用；
   - 條碼有多筆相符 → 無法唯一對應；
   - 沒有條碼，或條碼沒有相符 → 改用名稱比對：恰好 1 筆 → 採用；0 筆 → 商品缺失；多筆 → 無法唯一對應。
3. **只要有任何一個商品無法唯一對應**：
   - 以 `DEMAND_PRODUCT_REMAP_FAILED`（HTTP 409）拒絕；
   - 整次完整取代回滾，商品、訂單、登記、同意、分類、設定、會員都不變；
   - 不會回報成功；
   - 預覽階段就會顯示這個錯誤，無法進入正式匯入；就算直接呼叫正式匯入也一樣被拒。
4. **最終衝突檢查（C3.2 新增）**：
   - 依對應結果推算，若同一會員對同一個新商品會有兩筆有效（`status='active'`）登記，同樣以 `DEMAND_PRODUCT_REMAP_FAILED` 拒絕並回滾。
   - 典型情況：目前店裡有兩款同名商品，各自有同一會員的有效登記，而舊備份只有一款同名商品。
   - 明細的 `reason` 為 `final_conflict`，並列出新商品 ID 與相關登記 ID。
   - 這項檢查在任何更新之前完成。
5. **全部都能對應、也沒有最終衝突時：分兩階段更新（C3.2 修正）**
   - C3.1 是直接逐筆把 `product_id` 改成新值。遇到商品 ID 互換（801↔701），如果同一會員兩款都有有效登記，第一筆更新就會撞到有效登記的部分唯一索引 `(store_id, product_id, line_user_id) WHERE status='active'`，導致整批回滾，合法的還原無法完成。
   - C3.2 改成兩階段：
     - **第 1 階段**：要變動的列，`product_id` 先改成「每列唯一的負數暫存值」（`-資料列 id`）。這個值不會和任何真實商品 ID 或其他列相同。
     - **第 2 階段**：再改成最終商品 ID。因為上一步已確認最終狀態沒有重複，這一步也不會撞索引。
     - 完成後核對：不得殘留任何負數暫存值。
   - 可支援互換（A↔B）、三款以上的循環（A→B→C→A），以及任何不衝突的排列。
   - 唯一索引全程保留並生效，沒有刪除或停用任何去重約束。
   - 會員、份數、偏好、週期、有效期限、狀態、同意狀態，以及同意和登記的關聯，全部不動。
   - 全部在同一個交易內完成：預覽最後回滾，正式匯入失敗也會整批回滾。
   - 預覽與匯入結果都會附上 `demand_remap`，例如：`[{from:801,to:701,matched_by:"name",rows:5}]`。
6. 匯入過程不會呼叫任何 LINE 或推播 API。

### 被拒絕時怎麼辦

拒絕訊息會列出是哪些商品對不到、原因、以及受影響的登記／同意筆數。可以擇一處理：

- 改用包含「商品想買登記」分類的完整備份（C3 以後做的完整備份都有）；
- 確認舊備份裡的商品名稱或條碼，能唯一對應到現有登記的商品。

### 已知限制

後台可以**直接刪除商品**。商品被刪掉之後，它的登記會留在資料庫裡，只剩名稱快照。

如果之後用舊備份做完整取代，而備份裡沒有同名商品，該次完整取代就會被拒絕。這是刻意的選擇：寧可拒絕，也不讓那筆舊商品 ID 被新匯入的另一款商品「接手」。

本輪沒有修改刪除商品的行為。

## 四、版本相容與回退

- C3 以後做的完整備份含有新分類，C2 的匯入程式會以 `UNKNOWN_CATEGORY` 拒絕。
- 回退到 C2 時，請改用以下任一種備份：
  - C2 時期做的備份；
  - 在 C3 以後的版本用選擇性匯出、沒勾「商品想買登記」的備份。
- C3、C3.1、C3.2 的資料表結構完全相同，C3.1 與 C3.2 都沒有新增任何遷移，三版之間可以直接互相切換。
- `schema_version` 維持 2。
