## 2. 重現與根因

### 2.1 成立狀態

重現（未修改基準、正式路由、暫存資料庫、主機 TZ=UTC）：

- 待付款、付款失敗（顧客取消）、待核對的 LINE Pay 訂單，在「我的訂單」列表與詳情都顯示「訂單：已成立」。
  - 真實 Chrome 卡片：`付款：LINE Pay（付款失敗）｜訂單：已成立`、操作只有「🔄 再購」。
- 付款頁只有付款狀態，沒有訂單是否成立的資訊。
- 歷史付款證據：同一訂單「較早已付款＋較新一筆失敗」時，列表狀態顯示「付款失敗」；「較早待核對＋較新一筆失敗」時，付款狀態顯示「付款失敗」（不安全）。

根因：

1. `utils/popupOrderLookup.js` 的 `ORDER_STATUS_LABELS` 把 `pending` 與 `accepted` 一律翻成「已成立」，`order_status_label` 直接採用，完全不看付款。
2. `consumerStatus()` 只讀「最新一筆」付款紀錄，因此較新的失敗會推翻較早的已付款或待核對。
3. 成立判定沒有集中的後端來源：付款頁、我的訂單、後台各自依付款或履約欄位呈現。

### 2.2 時間

重現（未修改基準、可控時鐘、TZ=UTC）：

- UTC 2026-11-16T08:08Z 建立 → 建立時間 16:08（正確）。
- 08:09Z 各種更新 → 狀態更新顯示 08:09（應為 16:09）。
- 只有 LINE Pay 付款失敗時，更新時間停在 08:08。
- 廚房狀態更新顯示 `2026-11-16T08:09`（ISO 字串直接截取）。
- 付款頁「請於 HH:MM 前完成付款」在紐約時區瀏覽器顯示 03:24（應為 16:24）。
- 主機 TZ=Asia/Taipei 時只剩後兩者，因此既有測試（一律 TZ=Asia/Taipei）一直沒抓到。

根因：

1. `created_at` 由結帳以台北時間寫入（R53），但所有更新路徑使用 SQLite `datetime('now','localtime')`＝主機時區。
   - 涉及路徑：快閃付款、改現金、逾時、共用訂單狀態流程、作廢、退款、LINE Pay 共用服務。
   - 廚房寫入點則使用 ISO 帶 Z。
2. 付款失敗、待核對、改現金前的失敗等「只改付款紀錄」的路徑不更新訂單本身，訂單的「狀態更新」不會移動。
3. 前台把時間字串直接截取前 16 字；付款期限用瀏覽器本機時區 `getHours()`。

## 3. 後端統一判定規則與各畫面對照

### 3.1 判定（`utils/popupOrderStatus.js`，唯讀）

成立、付款、履約三者分開輸出：

- `establishment`／`establishment_label`／`established`（true／false／null＝待核對）
- `payment_status_label`
- `fulfillment`／`fulfillment_label`

付款狀態沿用 C5.4 的 `utils/paymentDisplay.derive`，多筆付款紀錄依可信證據合併：已付款 > 待退款 > 待核對 > 最新一筆的確定結果。

| 實際情況 | 成立欄位 | 列表徽章 |
|---|---|---|
| LINE Pay 有效、尚未付款 | 尚未成立，待付款 | 待付款（尚未成立） |
| 確定失敗／顧客取消本次付款 | 未成立，付款未完成 | 付款未完成（未成立） |
| 逾期但訂單未取消（店家關閉自動取消時） | 未成立，付款逾期 | 付款逾期（未成立） |
| 待核對、Confirm 已送出未定、處理階段不明的舊 pending | 付款結果確認中，請勿重複付款 | 付款結果確認中 |
| 後端確認付款（含店家現場確認收款） | 已成立 | 已成立／準備中／可取餐／已完成 |
| 現金（含成功改現金、0 元） | 已成立，取貨時付款 | 同上 |
| 轉帳、平台付款 | 已成立，待店家確認收款 | 同上 |
| 已取消、未付款 | 已取消；逾期者「已取消（付款逾期）」 | 已取消／已取消（付款逾期） |
| 已取消但已收款 | 已取消、已付款・待退款 | 已付款・待退款 |
| 退款完成 | 已取消、已退款 | 已退款 |

既有契約的處理（本輪不新增付款方式）：

- **轉帳、平台付款**：既有流程在下單時即保留名額，由店家確認收款，因此維持成立，付款文字為「待店家確認收款」。
- **舊版（未啟用快閃付款設定）**：沒有線上付款流程，線上付款方式也沒有付款紀錄，沿用店家確認收款契約；現金照常成立。
- **0 元**：快閃沒有 0 元專用流程，依付款方式契約處理。
- **不是所有 `payment_status='pending'` 都判未成立**：現金 pending 屬於已成立。

其他規則：

- 履約進度如實保留，不倒退或改寫。例如未付款但店家已接單：成立欄位「未成立，付款未完成」，進度「已接單」。
- 「未成立」是對外業務判定，不刪除付款證據、不釋放名額。
- 查詢不新增任何副作用（E10 以資料庫逐列雜湊驗證）。

### 4.1 契約

快閃訂單（`pickup_type='popup'`）的 `orders.created_at`、`orders.updated_at`：

- 格式：台北牆上時間 `YYYY-MM-DD HH:MM:SS`，無時區字尾。
- 這是既有欄位契約：R53 起 `created_at` 已如此；後台 `twTime()` 也把無時區字串視為台北。
- 欄位型別不變。

集中處理（`utils/popupOrderTime.js`）：

- 結帳：`taipeiString()`（固定 UTC+8；台灣自 1979 年不實施日光節約時間），結果與 R53 相同。
- 更新：兩個 SQLite 觸發器，只作用於快閃訂單，各寫入點不必自行處理：
  - `trg_c542_popup_order_updated_tpe`：任何寫入 `orders.updated_at` 的 UPDATE，都改為 `strftime('%Y-%m-%d %H:%M:%S','now','+8 hours')` 並標記來源。
  - `trg_c542_popup_attempt_touch_order`：快閃付款紀錄 `status` 改變時，同步更新該訂單的狀態更新時間。這解決「付款失敗只改付款紀錄」。
- 觸發器只寫 `orders.updated_at` 與來源標記，不改付款紀錄任何欄位。
- 不修改服務 `TZ`；前台不加 8 小時。

- 舊版寫下的 `updated_at=2026-11-16 08:08:02`：
  - 已付款者由 UTC 確認時間證實 → 顯示 16:08。

- 正式資料未操作；正式環境實際分布需部署後觀察。

## 9. 部署後最短真機驗收步驟

1. 在 LINE 開快閃場次，以 LINE Pay 下 1 元訂單，在 LINE Pay 頁按取消回到頁面。
   - 付款頁應同時顯示「付款狀態：付款失敗，本次付款未完成」與「訂單：未成立，付款未完成」，並可改用現金。
2. 開「📜 我的訂單」：
   - 該筆卡片應為「付款未完成（未成立）」、「訂單：未成立，付款未完成」，按鈕為「🔄 重新下單」。
   - 詳情的建立與狀態更新應是台灣時間，且狀態更新晚於建立（例如 16:08／16:09，不再是 08:09）。
   - 按「重新下單」只帶回商品選購，不應送單或付款。
3. 回到付款頁按「改用現金（取貨時付款）」：付款頁與我的訂單應改為「已成立，取貨時付款」。
4. 另下一筆 1 元並完成 LINE Pay 付款：應顯示「已成立」「已付款」。
5. 後台訂單列表：上述訂單的付款徽章旁應出現相同的「訂單：…」文字。
6. 選用：手機時區改為其他國家，付款頁「請於 HH:MM 前完成付款（台灣時間）」應仍為台灣時間。

LINE App 內建瀏覽器、iOS Safari、真實 LINE Pay 尚待真機驗證；舊資料出現「時區未確認」的比例需部署後觀察。
