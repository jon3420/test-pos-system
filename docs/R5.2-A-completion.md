# R5.2-A Completion Document
## fix18-10-hotfix30-B5-R5.2-A — Taiwan Administrative Area Intelligence

## 1. Release Scope

全台行政區智慧分析（Taiwan Administrative Area Intelligence）。將 R5.1 系列
只支援桃園市 13 行政區的 Geo Intelligence，全面提升為涵蓋全台 22 縣市／368
鄉鎮市區的正規化引擎、統一 API 行政區格式、行政區篩選、履約行政區代碼寫入，
並為未來商圈功能預留（但本輪不實作）資料欄位。

## 2. Completed Modules

- **Taiwan administrative dataset**：22 縣市／368 鄉鎮市區，來源
  Wikipedia「List of townships/cities and districts in Taiwan」（衍生自
  ROC 內政部鄉鎮市區統計代碼），parser 產生、程式化驗證。
- **Manifest / checksum**：`data/taiwan-administrative-areas.manifest.json`，
  含來源、抓取日期、筆數、SHA-256 checksum。
- **Normalization**：`normalizeCounty()` / `normalizeSubdivision()` /
  `resolveTaiwanAdministrativeArea()`，含台/臺別名、英文別名、六都以外全
  縣市/離島（金門、連江）覆蓋。
- **Filter validator**：`validateAreaFilters()`，統一
  `unknown_county_code` / `unknown_subdivision_code` /
  `subdivision_not_in_county` / `invalid_county_code` /
  `invalid_subdivision_code` 五種固定錯誤代碼。
- **resolveStoredArea()**：統一從「已存在的 DB 列」解析行政區，
  acquisition／fulfillment 兩種 context 完全隔離，有效官方代碼優先於名稱，
  無效代碼 fallback 名稱，只有 subdivision_code 時可反查 county。
- **Unified area enrichment**：`_enrichAreaFields()` 套用到
  `/overview`／`/funnel`／`/fulfillment`／`/source-area`／
  `/cart-attribution`／`/alerts`，統一輸出 `county_code` /
  `county_name` / `subdivision_code` / `subdivision_name` /
  `subdivision_type` / `area_key` / `area_label` / `resolution`，同時保留
  舊欄位（`city`／`district`／`geo_city`／`geo_district`）。
- **/overview area filtering**：county/subdivision 篩選真正影響
  `identified_visitors`／`unknown_visitors`／`identified_rate`／
  `top_areas`（非只篩 top_areas、totals 不動）。
- **/funnel area filtering**：同上邏輯，透過共用
  `_commonEventFilterClause()`。
- **Fulfillment analytics**（`/fulfillment`）：履約 context 專用篩選，
  絕不與 acquisition 混用。
- **County summary**（`/county-summary`）：縣市層級彙總，含
  `visitor_to_cart_rate`／`cart_to_purchase_rate`／
  `visitor_to_purchase_rate`／`unknown` 統計。
- **source-area / cart-attribution**：套用同一組 unified enrichment。
- **Mixed-context alerts**：`traffic_waste`／`checkout_drop`（acquisition）、
  `delivery_cost_risk`／`out_of_range_demand`（fulfillment）、
  `data_quality`（`geo_context:null`、`scope:'store'`），每個 alert 物件
  明確標記 `geo_context`，enrichment 依此動態判斷，同一回應可同時存在兩種
  context 且互不覆蓋。
- **Order fulfillment geo writes**：`routes/line-orders.js`（LINE 外送，
  經 `formattedAddress` 正規表達式解析）、`routes/line-shipping.js`（LINE
  宅配，結構化 `city`/`district`），兩者皆寫入
  `fulfillment_geo_county_code`／`fulfillment_geo_subdivision_code`，
  重用既有 `normalizeDeliveryGeo()` 已算好的代碼，未新增第二套解析邏輯。
- **Business-area reserved columns**：`analytics_events`／`orders` 各自
  新增 `business_area_code`／`business_area_name`，nullable、預設
  NULL，全專案零 writer、零 reader、零 API、零 UI。
- **Migration compatibility**：所有新欄位皆用「PRAGMA table_info 檢查 →
  ALTER TABLE ADD COLUMN」的既有安全 migration 慣例，未破壞 PRIMARY
  KEY／INDEX／UNIQUE／FOREIGN KEY／既有預設值，重跑 migration 冪等。
- **Privacy protection**：所有新增/修改 API 皆通過遞迴隱私掃描（無 raw
  IP、無完整地址、無電話/姓名、無 lat/lng、無 secret/token）。
- **Store isolation**：`/overview`／`/funnel`／`/fulfillment`／
  `/alerts`／`/county-summary` 皆已驗證跨店不互相污染。

## 4. Order Write Support

- **LINE 外送**（`routes/line-orders.js`）：支援。經
  `normalizeDeliveryGeo({formattedAddress: delivery_address, ...})`
  正規表達式解析後寫入 `fulfillment_geo_county_code`／
  `fulfillment_geo_subdivision_code`。
- **LINE 宅配**（`routes/line-shipping.js`）：支援。使用結構化
  `shipping_city`／`shipping_district` 輸入。
- **LINE 外帶**：兩個 fulfillment code 欄位固定 NULL（無履約地址概念）。
- **`routes/orders.js`**（POS/後台人工建單，含第三方外送平台）：**未支援**。
- **`routes/sync.js`**（POS 裝置訂單匯入）：**未支援**。

原因（兩者相同）：僅有原始 `delivery_address` 自由文字欄位或第三方
payload，沒有可靠的結構化 city/district 來源；本輪原則是「沒有結構化來源
就不猜地址」，不對這兩條路徑新增地址解析邏輯。

## 7. Known Limitations

- `routes/orders.js` 的訂單建立路徑未寫入 fulfillment 行政區代碼（只有原始
  `delivery_address` 字串／第三方平台欄位，無可靠結構化來源）。
- `routes/sync.js` 的訂單匯入路徑同樣未寫入（第三方裝置同步 payload，同一
  原因）。
- 沒有明確的多語句 transaction（BEGIN/COMMIT/ROLLBACK）包裹訂單建立
  INSERT——`routes/line-orders.js`／`routes/line-shipping.js` 目前都是
  sql.js 同步 API 的單一 `db.run()` 呼叫，本輪未重構這個既有架構。
- `orders.items` 目前是 JSON blob 欄位，不是獨立的 `order_items` 資料表。
- 商圈（business area）功能尚未實作——本輪只保留 DB 欄位，見第 5 節。
- 地圖視覺化（GeoJSON／Leaflet／行政區底圖著色）尚未實作，明確排除於
  R5.2-A 範圍外（R5.1-D 系列時就已決議延後）。
- 郵遞區號輔助解析（postal-code auxiliary resolution）：**NOT
  IMPLEMENTED**——尚未納入可靠且具版本資訊的全台郵遞區號資料集，避免用不
  完整或過時資料誤判行政區。行政區判斷目前僅透過官方行政區代碼、縣市/
  鄉鎮市區中英文名稱與已驗證別名進行。
- `/county-summary` 與 `/available-areas` 的 `geo_context=fulfillment`
  尚未真正實作（見上方 API Support Matrix），目前只支援 acquisition 統計
  口徑；`/available-areas` 的 subdivision 層級 `has_data` 欄位目前誠實回傳
  恆為 `false`（尚未接上真正的逐鄉鎮市區聚合查詢）。
- Live Provider Verification：本 sandbox 環境的網路白名單不含
  ip-api.com，無法在此環境驗證 Visitor IP Geo Provider 的成功查詢路徑
  （fail-open／錯誤處理／IP 遮罩路徑已驗證，但未驗證真正成功回傳資料的
  情境）。

## 8. Known Testing Notes

- **NON-REPRODUCIBLE TEST ANOMALY**：
  `smoke-hotfix31-r4-channel-visitor360.js` 的 assertion 11
  （「source 維度獨立於 channel：同一渠道下仍可依 source 區分」）在本次
  R5.2-A 開發過程中曾出現 1 次失敗（`sources.analytics_sources` 回傳
  `[]`），此後連續多次（isolated + full-sequence 合計 8 次以上）重跑皆
  100% 通過，未再重現。已記錄執行時間、系統時區（UTC）、失敗當下的完整
  輸出，但尚未查明根本原因。**不得標記為已修復**，僅標記為
  non-reproducible anomaly。
- **`smoke-hotfix26-f7.js` 過時 hardcoded 斷言**：此測試檢查
  `routes/line-orders.js` 的 `INSERT INTO orders` 欄位數是否等於寫死的
  `44`。已確認 pristine baseline（本輪修改前的原始碼）此斷言**本來就已經
  失敗**（`cols=51 ph=49`，欄位數與 placeholder 數本身就不一致，是一個
  更早期就存在、且從未被本輪修改觸發的 pre-existing bug）。本輪 Stage 8
  的修改實際上**修正**了這個底層不一致（現在 `cols=53 ph=53`，正確一致），
  但 `smoke-hotfix26-f7.js` 寫死的 `44` 本身已經跨越了 R5.1-A 到
  R5.2-A 之間所有合法新增的欄位（`geo_accuracy`／`geo_provider`／
  `geo_county_code`／`geo_subdivision_code`／
  `fulfillment_geo_county_code`／`fulfillment_geo_subdivision_code`
  等），因此仍然會顯示 FAIL。依據 Stage 9 指示，本輪**刻意不修改**這支
  legacy 測試（避免 scope 擴張），僅誠實記錄於此。同樣受影響的還有依賴它
  的 meta-runner（`smoke-hotfix26-f8-b.js`、`smoke-hotfix27.js`）。
- **`smoke-cart-delivery-live-refresh.js` 既有 3 個失敗**：與外送費即時
  更新的前端行為有關（`deliveryFeeCalculated`／`finalFee`／`reached`
  三個斷言），已確認在 pristine baseline 上同樣失敗（逐字相同的錯誤訊息），
  與本輪 Geo/行政區修改完全無關，不得描述為本版 regression。
- **`smoke-hotfix26-e.js`／`smoke-hotfix26-i.js` 逾時或既有失敗**：
  `smoke-hotfix26-e.js` 是一個會依序執行多支其他 smoke test 的 meta-runner，
  在 pristine baseline 上同樣會逾時（此環境下常態超過測試逾時上限）；
  `smoke-hotfix26-i.js` 的失敗（`openOaBtn.removeAttribute is not a
  function`）是 jsdom 模擬 LINE OA 按鈕 DOM 操作的既有問題，同樣在
  pristine baseline 上逐字重現。兩者皆與本輪修改無關。
