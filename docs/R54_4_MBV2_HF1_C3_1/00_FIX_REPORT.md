## 一、舊備份完整取代後，登記的商品關聯錯掉

### 根因

1. 完整取代會清除商品，再依備份檔的商品 ID 重新建立。
2. 舊備份沒有 `product_demand` 分類，所以登記與同意會被保留。
3. 但保留下來的登記與同意，`product_id` 沒有跟著重新對應，仍是舊的 ID。

### 在 C3 重現

用本輪新增的測試（R 段）在 C3 執行：

- R1：登記仍指向 801，但商品已經變成 701，後台顯示 701 有 0 人。
- R2：備份裡的 801 是另一款商品「測試對照湯」，C3 的登記就**指錯**到這款商品上。
- R3／R4：商品缺失、或同名無法唯一對應時，C3 仍然匯入成功，留下孤兒資料。

C3 這段結果：**4 通過／22 失敗**。

### 修正（`utils/migrationV2.js`）

只在「完整取代、有選商品資料、但沒有選想買登記」時啟用：

1. **清除商品之前**，記下每個被登記或同意引用的商品識別：條碼、名稱；商品已不存在時用名稱快照。
2. **商品重建之後**，依「條碼 → 名稱」找到唯一的對應商品，**不假設數字 ID 不變**。
3. **只要有一個商品對不上**（缺失或多筆）：
   - 以 `DEMAND_PRODUCT_REMAP_FAILED`（HTTP 409）拒絕；
   - 整批回滾，資料完全不變；
   - 訊息列出是哪個商品、原因、影響幾筆。
4. **全部對得上時**：逐筆更新登記與同意的商品關聯，會員、份數、偏好、狀態、期限、週期、同意狀態都不動。
5. **預覽與正式匯入共用同一段程式**：
   - 預覽就會看到對應結果（`demand_remap`）或拒絕原因；
   - 就算略過預覽、直接呼叫正式匯入，也一樣被拒。
6. 不呼叫任何通知。

失敗明細會一起回傳（`demand_remap_failures`），包括 API 回應和工作狀態裡的 `job.error`。

詳細說明見 `03_BACKUP_RESTORE_DEMAND.md`。

## 二、既有登記需要一直找得到的管理入口

### 根因

C3 的商品卡、詳情只靠 `_demandEntryAllowed()`（也就是「能否新增登記」）決定要不要顯示按鈕。

所以商品恢復販售、被關閉收集、或功能整體關閉之後：

- 本人明明還有有效登記，「已登記／管理登記」卻消失了；
- 商品被隱藏或停用之後，完全沒有地方可以管理。

C3 這段結果：**5 通過／9 失敗**。

### 修正

**分開判斷「能否新增」與「能否管理」**

- `_demandEntryAllowed()`：能否**新增**。條件不變：入口條件＋功能開關＋商品收集開關。
- `_demandManageAllowed()`：能否**管理**。只看本人是否有有效登記，不受商品狀態或收集設定影響。
- 商品卡、詳情只要符合其中一個就顯示入口。
- 詳情裡，「管理登記」可以和「加入購物車」並存（`product-detail-modal.js` 不再限定只有無法加入時才顯示，是否提供改由呼叫端決定）。

**頁首新增固定入口「🙋 我的想買登記」**

- 顯示條件：已登入，且「功能開啟」或「本人仍有登記」。
- 打開後列出本人的所有有效登記，**包含目前已隱藏或停用的商品**（只顯示名稱與登記內容）。
- 每一筆都可以點「管理」。

**唯讀管理**

- 不能修改份數時（收集關閉、功能關閉、商品隱藏或停用），表單只提供：查看、取消登記、撤回通知同意。
- 要修改份數，仍然以最新設定為準：
  - 後端 `/mine` 回傳 `can_modify`；
  - `register()` 會再檢查一次，不符合就回 403。

**不會讓商品重新曝光**

- 隱藏的商品不會回到 `/api/line-menu` 或 `allProducts`，不會出現商品卡，也不能下單（測試中下單回 400）。
- `/mine` 只回傳**本人**登記用到的商品名稱。

**隔離**

- 其他會員取消別人的登記 → 404。
- 其他店別的 session → 401。
- 不管商品卡有沒有顯示都一樣。

## 三、LINE 登入導回的初始化順序

### 根因 1：`_initProductDemand()` 太早刪掉待恢復紀錄

C3 在確認是否已有會員 session **之前**，就先刪掉了 `pd_pending_open`。

如果會員驗證比較慢，這次初始化會把待恢復紀錄刪掉；之後 session 才出現，也不會再開回表單。

### 根因 2：`_memberGateInitPromise` 的作用域錯誤（既有問題）

- 這個變數用 `let` 宣告在 `if(sr.success){…}` 區塊裡面。
- 區塊外的 `await` 讀不到它，產生 ReferenceError，被 `catch` 吃掉。
- 結果是：**實際上從來沒有等待過**會員 Gate 初始化。

C3 這段結果：**5 通過／8 失敗**。

### 修正

**作用域**

- 把 `let _memberGateInitPromise` 移到 `if(sr.success)` 之前。
- 頁面層的 `try{ await _memberGateInitPromise; }` 現在會真的等待。
  - 這就是 H1.4.10 原本設計的順序：先 restoreCart，再等會員 Gate，最後跑 Recovery bootstrap。
  - 也和 `line-shipping.html` 現行的行為一致。

**登記恢復**

- `_initProductDemand(gatePromise)` 會完整等待會員 Gate 完成後，才判斷有沒有 session。
- **待恢復紀錄只在三種情況才會被消耗**：
  - 已登入並成功重開表單；
  - 使用者按 ✕ 或點遮罩，明確關閉；
  - 超過 10 分鐘有效期。
- **沒有 session 時**：
  - 表單先以「需要登入」的狀態開啟，**保留**待恢復紀錄；
  - 每秒檢查一次，切回頁面（focus／visibilitychange）時也會檢查；
  - session 一出現，就在**同一次開啟**中轉成登記表單。
- **驗證失敗**：顯示錯誤、保留紀錄，可以重新嘗試。
- **session 過期**：
  - 後端回 401 → 顯示「LINE 會員登入已過期」和「重新以 LINE 登入」；
  - 本機 session 已逾時 → 當作未登入處理。
- **只恢復一次**：同一頁面最多恢復一次，紀錄消耗後重新整理也不會再開。
- **一般瀏覽者**：沒有待恢復紀錄時不會開表單、不要求登入，頁首入口也不顯示。
- 執行順序維持：restoreCart → await 會員 Gate → `_initProductDemand`（不阻塞）→ Recovery bootstrap。

## 六、需要特別知道的行為變更

1. **LINE 點餐頁初始化現在會真的等待會員 Gate**（作用域修正後的結果）。

## 七、部署後最短驗收

1. **管理入口**
   - 用 LINE 登入，對一個暫停販售的商品按「我想買」，登記 2 份。
   - 在後台把它改回正常販售：商品卡可以加入購物車，同時仍顯示「已登記 2 份・管理登記」；頁首出現「🙋 我的想買登記」。
   - 後台「🙋 想買登記」關閉該商品的「收集」：重新整理後，從頁首清單點「管理」，畫面是唯讀，可以取消登記。取消後清單變空。
2. **登入導回**
   - 用未登入的狀態，在 LINE 裡按「我想買」→「以 LINE 登入」。
   - 導回後，表單會自動重開**一次**，可以直接送出。
   - 重新整理後不會再自動開啟。
3. **備份**
   - 匯出一份「完整備份」。
   - 在測試店用沒有「商品想買登記」分類的舊備份做完整取代預覽：
     - 商品可以對應時，預覽會列出 `demand_remap`；
     - 無法對應時，預覽會被拒絕，資料完全不變。
4. **C3／C2 最短驗收照舊**：停售商品不顯示可預購；今日完售可以預購明天；詳情的額度上限正常。
