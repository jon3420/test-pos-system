## 一、根因（已在 C2 實際重現）

### 1. 停售商品又出現「可預購＋加購」

商品販售狀態的判斷散落在好幾個地方，彼此不一致：

- `_productModeStatus()` 已經把人工停售擋下，回傳 `canNextDay:false`。
- 但下面這些函式又各自直接讀後端的原始 `takeout_can_next_day`／`delivery_can_next_day`：
  - `buildCard()`
  - `openProductDetail()`
  - `updateProductCard()`
  - `resolveCartQuantityPolicy()`
  - `refreshDateSelectorForCart()`
  - `productRequiresNextDayPreorder()`
- 後端 `/api/line-menu` 計算原始次日旗標時，完全沒有看 `sale_status`。所以「販售時段已結束（`product_time_ended`）＋允許次日預購」時，停售商品的原始旗標仍是 `true`。

用同一支新測試在 C2 重現（例：長期下架＋販售時段結束）：

```
商品卡標示「🔴 今日售完 🟢 可預購」、有可用的＋
checkCartIncrement() 回傳 ok=false（實際加不進去）
```

C2 執行新測試的 S、O 兩段，結果 172 通過／92 失敗。失敗項目包括：

- 暫停販售／長期下架在「販售結束」時段，畫面與實際操作不一致。
- 舊購物車還原、局部更新、重新整理、載入最新商品資料後，同樣不一致。
- 長期下架被標成「今日售完」。
- `/api/line-menu` 對停售商品回傳 `can_next_day=true`。

### 2. 今日完售不能預購未來日期（C2 原本的行為）

- 前台：`_productModeStatus()` 對所有「非正常販售」的商品一律回傳不可購買。
- 後端 `POST /api/line-orders` 有兩道阻擋：
  - 送單前的檢查：只要 `sale_status === 'sold_out_today'` 就拒絕，不管訂單日期。
  - 交易內重新讀取商品時：`sale_status !== 'available'` 也拒絕。
- `/api/line-menu` 對今日完售的商品不會給出可預約旗標。

### 3. 預購已滿時仍顯示可用的＋（本輪測試另外發現，C2 也有）

- 畫面顯示「預購已滿」徽章，同時有可用的＋。
- 按下去才被擋。這跟第 1 點是同一類「畫面與實際操作不一致」的問題。

## 二、實作

### A. 統一有效判斷（`public/line-order.html`）

新增共用判斷：

- `getEffectiveSoldOutReason()`／`getEffectiveCanNextDay()`
  - 暫停販售、長期下架：一律不可預約，任何今日原因或原始次日旗標都蓋不過。
  - 今日完售：今日一律不可下單；能不能預約未來日期，沿用後端計算的旗標。
- `computeProductSaleView()`：商品卡、詳情、局部更新三處共用的唯一計算。
- `_cardFooterHtml()`：`buildCard()` 和 `updateProductCard()` 共用的加購區塊。
  - 可加購時：顯示＋。
  - 不可加購但購物車已有：顯示「− 數量 ＋（停用）」，只能減少或移除。
  - 預購已滿：不提供＋。
- 下列函式全部改用上面的有效判斷，畫面已經不直接讀原始 `can_next_day`：
  - `_productModeStatus()`
  - `resolveCartQuantityPolicy()`
  - `productRequiresNextDayPreorder()`
  - `refreshDateSelectorForCart()`

標示依人工狀態優先：

- 暫停販售 →「暫停販售」
- 長期下架 →「長期下架」
- 人工今日完售 →「今日完售」
- 自然售完 → 維持「今日售完」

其他：

- 購物車中的停售商品：＋改成停用樣式，按了只會提示原因，不會增加。
- 沒有硬編碼任何商品名稱或 ID。

### B. 後端

**`GET /api/line-menu`**

- 暫停販售／長期下架：`*_can_next_day` 一律回 `false`。
- 今日完售：該通路沒被商品自身或店家關閉、且店家允許次日預購時，回 `true`。
- 正常販售：沿用原本的計算。

**`POST /api/line-orders`**

- 新增 `checkManualSaleStatusForOrder(prod, isPreorderOrder)`，送單前檢查與交易內重新檢查**共用**這個函式：
  - 正常販售：通過。
  - 今日完售：今日訂單擋下；未來日期通過，再走既有的預購額度檢查。
  - 暫停販售／長期下架：任何日期都擋下。
- 沒有改寫商品的 `sale_status`，沒有放寬其他狀態，也沒有略過交易內的重新檢查。
- 未來訂單一律記在預購額度（既有的 `line_counter_bucket='preorder'`），不扣今日額度。
- 新增 `validateFutureOrderWindow()`：
  - 適用所有未來日期訂單，人工今日完售和自然售完走同一套。
  - 該日該通路沒有營業時段 → 拒絕。
  - 有指定取餐時間時，必須落在該日的營業時段內。
  - 營業時段的來源和 `GET /timeslots` 相同。
  - **這是對所有未來訂單的收緊。** 正常流程不受影響，因為前台只會提供 `/timeslots` 給出的時段。
- `GET /validate-cart` 也套用同一個販售狀態判斷。

**沿用不變的部分**

- 今日完售的「隔日恢復」設定：`server.js` 的自動恢復排程沒有修改。
- 未啟用預購份數管理的商品：照舊不限額，不會被當成禁止預購（驗收 O9）。

- 店家功能開關開啟；
- 該商品的收集開關開啟。

隱藏規則照舊：`enabled=0`、`show_on_line=0`、外帶與外送都停用的商品，不會出現，也不能登記。

**顧客文案**

文案依需求文件逐字使用：

- 本輪的登記模式：「我想買」「這款商品，你想買幾份？」「送出登記」「已收到你的想買登記，謝謝！」「已登記 2 份・管理登記」。
- 通知模式：已經寫好，**只有在後端回報 `notify_available=true` 時才會顯示**。本輪後端固定回報 false。
- 兩種模式都顯示免責文字。
- 沒有使用「登記補貨需求」或「立即」。

**按鈕行為**

- 按鈕位置：在停售標籤所在的商品內容區塊下方，不在圖片遮罩上。
- 實測窄版 2 欄（390px）與桌面 3 欄（1280px），按鈕都在卡片內、中心點可以點到。
- 點按鈕時不會開啟詳情，也不會觸發加購或購買事件，不送 `add_to_cart`、`view_item`、`purchase`。

**資料規則**

- 同一店別＋商品＋會員，同一有效週期只會有一筆。用資料庫的部分唯一索引保證，寫入在同一個交易裡完成。
- 重複送出：只會回「沒有變更」或「已更新」，不會增加人數，也不會累加份數。
- 取消或過期後重新登記：開新的週期。
- 統計排除已取消和已過期的登記。
- 登記、修改、取消都不會建立訂單、收款、扣額度或保留庫存（驗收 D23、D24）。

   - 加入購物車後，日期會自動跳到下個營業日；
   - 送出後，後台的預購已售增加，今日已售不變。
4. **還原與 C2 回歸**：把商品恢復成正常販售，再跑一次 C2 的最短驗收（預購 20 份達上限時，詳情顯示「預購額度已達上限」）。

## 六、功能開關

| 開關 | 位置 | 效果 |
|---|---|---|
| 想買登記總開關 `product_demand_enabled` | 後台「🙋 想買登記」→「在 LINE 點餐頁顯示…」 | 關閉後前台不顯示入口，登記 API 回 403。已存在的登記保留 |
| 個別商品收集開關 `products.demand_collect_enabled` | 同一分頁每一列的「收集」 | 關閉後該商品不顯示入口，也不能登記 |
| 登記有效天數 `product_demand_ttl_days` | 同一分頁 | 1～180 天，預設 30 天 |
| LINE 補貨通知 | 程式常數＋設定 `product_demand_notify_enabled` | 本輪程式常數是 false，所以即使設定開啟也不會生效 |

販售狀態的修正沒有開關，屬於錯誤修正。

## 七、回退

- 資料庫只做了**新增**：
  - 兩張新表；
  - `products.demand_collect_enabled` 欄位；
  - 三個設定值。
- C2 程式不會讀這些新增的東西，所以**直接重新部署 C2 ZIP（`7e09ba87…`）即可回退，不需要動資料庫**。
- 回退後的行為：
  - 已存在的登記會留在資料庫裡，但不會顯示；
  - 今日完售回到「不能預購」；
  - 停售商品又會出現 C2 的畫面不一致。
- 只想關掉想買登記、保留販售狀態修正：在後台把「想買登記總開關」關閉即可，不需要回退版本。
- **備份相容性**：C3 做出來的「完整備份」含有新分類，C2 的匯入程式會拒絕。回退前請改用以下任一種：
  - C2 時期的備份；
  - 在 C3 用「選擇性匯出」、沒勾「商品想買登記」做出的備份。
- 詳見 `03_DEMAND_SCHEMA_AND_MBV2.md`。
