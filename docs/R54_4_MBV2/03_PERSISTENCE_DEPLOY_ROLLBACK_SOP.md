# R54.4-MBV2 SQLite 持久化稽核、環境變數、正式部署 SOP、回滾 SOP

> 本次**沒有部署任何環境**，也沒有讀取或修改正式資料庫。Zeabur 實際設定（Volume、環境變數、記憶體規格）本環境無法讀取，以下標示「待確認」的項目必須由店家在 Zeabur 後台確認。

## 一、SQLite 持久化稽核（Phase 9）

| # | 項目 | 稽核結果（依原始碼與實測） |
|---|---|---|
| 1 | SQLite 實際路徑 | `utils/db.js`：`POS_DB_PATH` 有設定就用它，否則 `<程式目錄>/data/pos.db`（Zeabur 通常是 `/app/data/pos.db`，**待確認**） |
| 2 | 是否位於容器暫存檔案系統 | 未設定 `POS_DB_PATH` 時位於程式目錄內 → 屬於容器映像層，**重新部署即遺失**，除非 Volume 正好掛在 `/app/data` |
| 3 | 是否掛載持久化 Volume | **待確認**。注意：如果把 Volume 掛在 `/app/data`，會蓋掉 ZIP 內的 `data/geo/`、`data/taiwan-administrative-areas.json`（地理功能需要），所以**不建議**掛在 `/app/data` |
| 4 | DB_PATH 設定 | `.env.example` 有 `DB_PATH=`，但**程式從未讀取 `DB_PATH`**。只設 `DB_PATH` 等於沒設。R54.4-MBV2 起啟動時會印出 `STORAGE_WARNING`，設定頁也會顯示提醒；刻意**不**自動改用 DB_PATH（否則部署後會突然改讀另一個檔案） |
| 5 | WAL／SHM | 不適用。sql.js 是整份資料庫載入記憶體、以 `export()` 整檔寫出，**不使用 WAL／SHM**。`runDurableTransaction` 為 temp＋fsync＋rename 原子替換；一般 `db.run()` 為 `writeFileSync` 覆寫 |
| 6 | 備份一致性 | V2 匯出在單一同步流程內讀完所有表（期間不會有其他寫入），是一致快照。直接複製 `pos.db` 檔也可，但請在服務停止或低峰時複製 |
| 7 | 資料庫能否成功還原 | ✅ 已驗證：V2 完整備份匯入全新環境，各表筆數一致、交易內核對通過（測試 I2）；完整取代前自動建立的 `.sqlite` 快照可直接開啟（測試 R6c） |
| 8 | 重新部署是否更換儲存位置 | 路徑本身固定；但若路徑在容器內（未掛 Volume），重新部署＝全新容器＝空資料庫。啟動時若資料庫檔不存在會印 `STORAGE_NOTICE` 並在設定頁提醒 |
| 9 | 未來遷移其他伺服器 | 兩種方式：(a) 複製 `pos.db` 檔到新主機的 Volume 並設定 `POS_DB_PATH`；(b) 舊站「完整匯出」→ 新站「完整匯入（跳過已存在）」，可用 `.json.gz` |

另外兩個會隨重新部署遺失的東西：
- **商品圖片**：存在 `public/uploads/`（程式目錄），資料庫只存網址，任何備份都不含圖片檔。
- **搬家暫存檔**：在系統暫存目錄，本來就是暫時性的（2 小時清除），不影響資料。

### 建議的安全持久化方案
1. 在 Zeabur 為服務建立 Volume，掛載路徑 **`/data`**（不要掛在 `/app` 或 `/app/data`）。
2. 設定環境變數 `POS_DB_PATH=/data/pos.db`。
3. （建議）商品圖片也需要持久化：可另掛 Volume 到 `/app/public/uploads`。這會隱藏 ZIP 內同路徑的檔案；目前 ZIP 不含 `public/uploads/`，因此不影響。
4. 部署後到「系統設定 → 資料備份／搬家」，頂端**不應**出現「資料庫檔位於程式目錄內」或「啟動時資料庫檔不存在」的提醒；也可呼叫 `GET /api/migration/v2/storage-status`（需店家登入）確認 `inside_app_directory=false`、`configured_by=POS_DB_PATH`。
5. 重新部署（或重新啟動）一次，確認訂單筆數不變，才算完成持久化驗證。

## 二、環境變數清單（本次相關）

| 變數 | 必要 | 說明 |
|---|---|---|
| `POS_DB_PATH` | 正式站**必要** | 資料庫檔完整路徑，必須位於持久化 Volume，例如 `/data/pos.db` |
| `DB_PATH` | 否 | **無作用**（程式不讀取）。只設它會出現警告 |
| `MIGRATION_UPLOAD_LIMIT_MB` | 否 | 搬家上傳上限，預設 **192**，最高 **256**（填更大會自動限制為 256）；同時限制 `.json.gz` 解壓後大小 |
| `MIGRATION_TMP_DIR` | 否 | 上傳暫存目錄；預設 `<系統暫存>/pos-migration-v2` |
| `MIGRATION_SAFETY_DIR` | 否 | 完整取代前安全快照目錄；預設 `<資料庫同目錄>/migration-safety`（每店保留最近 5 份） |
| `NODE_OPTIONS` | 依資料量 | 例如 `--max-old-space-size=1536`。見下方記憶體需求 |
| `JWT_SECRET` | 正式站必要 | 既有；搬家 V2 與舊搬家路由現在都只接受 JWT |
| `TZ` | 建議 | 建議 `Asia/Taipei`，讓 POS 收銀建單的 `created_at`（DB 預設 `localtime`）與 LINE 訂單一致。**變更前請先確認目前值**，避免歷史資料前後時區混用 |

不需要新增任何 secret；本次沒有寫入任何金鑰值。

### 記憶體需求（實測，見測試報告 L10–L19）
| 匯入檔（解壓後） | 伺服器行程 RSS 峰值 | 備註 |
|---|---|---|
| 185MB（25.5 萬筆事件） | 約 1.6–1.7GB | heap 1GB 可完成；heap 512MB 會被記憶體保護擋下（507），不會讓 POS 中斷 |
| 250MB（純填充） | 約 0.7GB（只到上傳解析階段） | — |
- 匯入期間 Node event loop 被同步匯入佔用（185MB 約 30 秒），**收銀與 LINE 點餐會暫停回應**。大型匯入請在打烊後進行。
- 記憶體保護：解析前若可用 heap 小於「檔案大小 × 4 ＋ 64MB」，直接回 507 並提示分批，不會進入解析。

## 三、正式部署 SOP

> 原則：**先備份、再驗證持久化、最後才部署**。正式環境未完成備份與持久化驗證前，不要重新部署。

**A. 部署前（舊版仍在線上）**
1. 打烊或低峰時段。
2. 在舊版（R54.4）後台「系統設定 → 資料備份／搬家」按「下載快速搬家檔」，保存檔案（這是舊版格式完整備份）。
3. 若 Zeabur 可進入 Volume／檔案：另外複製一份 `pos.db`（及 `public/uploads/`）。
4. 在 Zeabur 確認：Volume 是否存在、掛載路徑、`POS_DB_PATH` 是否已設定。記錄目前所有環境變數（只記名稱與是否有值，不要把密鑰貼到聊天或文件）。
5. 確認 Zeabur 服務記憶體規格（建議 ≥ 2GB 才處理 100MB 以上的匯入）。

**B. 若持久化尚未設定（資料目前在容器內）**
1. 先建立 Volume（掛 `/data`），**暫時不要**設定 `POS_DB_PATH`。
2. 用目前（舊）版本做完 A-2 的完整備份並確認檔案可開啟。
3. 設定 `POS_DB_PATH=/data/pos.db` 後部署新版：新版會在 `/data` 建立空資料庫（啟動時會提醒「資料庫檔不存在」）。
4. 立刻用新版「匯入快速搬家檔 → 跳過已存在」匯入 A-2 的檔案（舊版格式可直接匯入），預覽確認筆數後執行。
5. 核對：訂單、商品、會員、事件筆數與匯入結果一致；店家登入密碼：新資料庫的密碼會是預設值（= 店家代碼），**請立即在總控台重設密碼**（`pos_password` 刻意不隨備份搬移）。
6. 重新啟動服務一次，確認資料仍在。

**C. 若持久化已正確設定**
1. 上傳本 ZIP 部署（ZIP 根目錄即程式根目錄；不含 node_modules、.env、資料庫）。
2. 部署後開啟後台：設定頁不應出現持久化警告；隨機抽查今日與歷史訂單。
3. 執行一次「完整匯出」確認新版可正常下載。

**D. 部署後煙霧測試（5 分鐘）**
- 收銀建一筆測試單 → 訂單紀錄可看到 → 作廢。
- LINE 點餐頁開得起來；快閃入口開得起來。
- 「資料備份／搬家」：匯出預覽有筆數；選「訂單紀錄＋指定月份」可下載。

## 四、回滾 SOP

**應用程式回滾**
1. 在 Zeabur 重新部署 R54.4 ZIP（SHA-256 `27667eda66658af84dc35e495d1232030f8d042c56352e4a86ea7e1651cef80d`）。
2. 本次**沒有任何 schema 變更或 migration**：R54.4 可直接使用 MBV2 期間的資料庫。MBV2 只新增 `migration_logs` 紀錄（舊版本來就會建立此表）。
3. 回滾後的已知差異：舊版搬家路由恢復接受 `x-store-id`（安全修正跟著回退）；上傳上限回到 25MB／100MB。

**資料回滾**
- 若是「完整取代」造成問題：安全快照在 `<資料庫目錄>/migration-safety/pre-replace-<店家>-<時間>.sqlite`。停止服務 → 先把目前 `pos.db` 另存 → 用快照檔取代 `pos.db` → 啟動。（快照是整份資料庫，會連同其他店家一起回到快照當時。若有多店同時營運，改用「完整匯入」只還原該店。）
- 若是「跳過已存在／安全合併」匯入了不想要的資料：這兩種模式不會刪除或覆蓋任何既有值（合併只補空白欄位），可用部署前的完整備份在測試環境比對後，再以完整取代還原該店。
- V2 完整備份檔同時帶有舊版 `type: pos_migration_backup` 標記，回滾到 R54.4 後仍可用舊版匯入器匯入（舊匯入器有上述欄位遺失問題，僅作為最後手段）。部分備份檔舊版會拒絕（刻意設計，避免舊版「清空後還原」清掉未包含的資料）。
