## 2. 問題與根因

### 2.1 重現（未修改基準，真實 Chrome）

| 情境 | 基準行為 |
|---|---|
| 按「前往 LINE Pay 付款」→ 409（付款結果確認中）延遲；期間「重新查詢付款狀態」已顯示「已付款」 | 舊 409 送達後，畫面被重畫成「付款結果確認中」 |
| 同上，操作改為「改用現金」 | 同樣被蓋回「付款結果確認中」 |
| 回應延遲期間，顧客用瀏覽器上一頁回到另一個場次 | 舊付款頁被拉回，取代場次二的選購頁。付款操作重畫成確認中；改現金重畫成取貨時付款 |
| 切到場次二再切回原場次一 | 同樣被拉回舊付款頁 |
| 畫面已改為顯示另一筆（已付款）付款 | 被覆蓋成舊付款的確認中或取貨時付款 |
| 「我的訂單」切換帳號後又以同一支電話登入 | 舊身份的 409 照樣重畫 |
| 付款建立**成功**但回應延遲，期間已回到場次二 | **仍執行過時導向**，頁面被帶到 LINE Pay 付款網址（以本機替身頁攔截） |
| 改現金成功但回應延遲，期間已回到場次二 | 付款頁被拉回 |
| 舊付款操作尚未回應時，畫面已換成另一筆待付款的付款 | 新畫面的付款按鈕**按了沒有反應**：全域 `paymentCreating` 被舊操作占住，請求沒有送出 |

### 2.2 根因

上一輪新增「後端拒絕時依回傳摘要重畫」的分支，只確認 `json.data.ref===ref`，也就是回應與當初傳入的付款識別相同。這不能說明操作仍然有效：

- 沒有確認原付款畫面是否還在、是否已被替換，包括同一付款識別重新顯示的新畫面。
- 沒有確認之後是否已有較新的查詢或操作更新了畫面。
- 沒有確認場次或帳號是否已切換。

除了 409 分支，這兩個函式的**成功重畫、付款網址導向與錯誤提示**原本也都沒有範圍檢查。上一輪之前的成功導向本來就有這個時序缺口，本輪一併修正。

此外，`popupUiState.paymentCreating` 是全域旗標，舊操作未完成時，另一筆付款的按鈕會被鎖住。

## 3. 修正（只改 `public/line-order.html`）

### 3.1 操作有效範圍（同檔小型共用 helper）

操作開始時，`popupPayOpBegin(kind, ref, btn)` 記下本次操作的範圍：

| 範圍項目 | 用途 |
|---|---|
| `view` | 目前付款畫面**物件**，沿用既有 `_popupPayView`。每次重畫都是新物件，所以同一付款識別重新顯示也算不同畫面 |
| `ref` | 付款識別 |
| `statusSeq` | 沿用既有 `_popupPayStatusSeq`。任何新查詢、付款畫面重畫、帳號切換都會讓它前進 |
| `sessionGen` | 新增 `_popupPaySessionGen`。進入或切換場次時遞增：非靜默載入場次、場次選擇畫面、瀏覽器上一頁回到場次列表 |
| `identityGen` | 新增 `_popupPayIdentityGen`。「切換帳號」，或已登入身份被換掉或登出時遞增 |
| `sessionCode` | 目前場次代碼（輔助比對） |
| `id` | 本次操作序號 |

- 按鈕不屬於目前付款畫面時，不送出操作。
- 回應到達後，`popupPayOpIsCurrent(op)` 只有在以上全部仍相符，且目前畫面仍是付款畫面時才為真。
- 版本只會遞增，所以**切換後再切回原場次或原帳號，舊操作也不會重新取得資格**。判斷不只比較當下的字串。

### 3.2 兩個函式內的副作用

| 副作用 | 修正後 |
|---|---|
| 成功重畫（改現金） | 只有有效範圍才重畫 |
| 付款網址導向 | 只有有效範圍才 `location.assign`。安全網址規則 `popupSafeLinePayUrl` 不變 |
| 409 依摘要重畫 | 只有有效範圍才重畫，保留上一輪的 `ref` 比對 |
| 錯誤提示（無法前往、網路異常、無法改現金） | 過時操作不寫入 |
| `finally` 清理 | 只釋放本操作自己的進行中標記，只還原本操作自己的按鈕。舊畫面的按鈕已不在畫面上；新畫面的按鈕是另外建立的，不受影響 |
| 忙碌狀態 | 由全域單一旗標改為「同一付款識別、同一種操作」一次一個：同一筆付款仍不會重複送出，另一筆付款不再被鎖住。`popupUiState.paymentCreating` 仍代表是否有付款建立進行中 |
| 同一筆付款重複點擊 | 不送出，並提示「付款建立中，請稍候；也可按『重新查詢付款狀態』確認」（原本沒有任何回饋） |

丟棄過時回應時：

- 不宣告未付款、不補送 POST、不自動重試、不再次改現金。
- 顧客已不在這筆付款的畫面上時，沿用既有提示「付款結果可至「📜 我的訂單」查看，請勿重複付款」。
  - 同一付款識別在本頁只提示一次。
  - 不覆蓋正在顯示的其他提示。
  - 不表示成功或失敗。
- 仍在同一筆付款的較新畫面上時，不另外提示。
- 後續狀態以有效查詢為準。

### 3.3 保留的既有行為

- C5.4.1 查詢中停用、回饋、12 秒等待上限與重試：原樣，回歸 19／19。

## 7. 部署、回退與尚未執行的驗收

- **部署**：本輪沒有資料庫遷移；部署新 ZIP 即可。本輪未部署。
- **回退**：直接部署 PAYMENT_GUARD_TIME_MERGE_FIX ZIP。後端相同，資料不需處理；整單付款防護與時間標記合併修正都仍保留。
- **回退會重新出現本次前端時序問題**：
  - 較晚回來的付款或改現金回應會覆蓋已付款或另一筆付款的畫面，並把舊付款頁拉回。
  - 付款建立成功但延遲時，可能執行過時導向。
  - 舊付款操作未回應時，另一筆付款按鈕可能暫時無反應。
  - 這些只影響畫面，後端狀態與名額仍正確；顧客重新查詢付款狀態或到「我的訂單」即可看到正確結果。
- **LINE 真機驗收：尚待進行**（本輪沒有呼叫真實 LINE、LINE Pay 或 Sandbox）。最短步驟：
  1. 在 LINE 內建瀏覽器開啟快閃場次，以 LINE Pay 結帳。到付款畫面先不付款。
  2. 開啟慢速網路（或飛航模式切換），按「前往 LINE Pay 付款」，立刻按「重新查詢付款狀態」或返回場次頁。確認恢復網路後畫面不被拉回、不自動跳到 LINE Pay。
  3. 正常網路下按「前往 LINE Pay 付款」，確認仍正常進入 LINE Pay 付款頁並完成付款，返回後顯示已付款。
  4. 另建一筆，付款失敗或取消後按「改用現金」，確認顯示取貨時付款、後台名額只成立一次。
  5. 付款畫面開「📜 我的訂單」→ 切換帳號 → 重新登入，確認付款畫面維持原狀且按鈕可用。
