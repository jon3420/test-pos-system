## 1. 五項問題：根因與前後結果

本輪先在**未修改的 C4**（另一份工作樹，只加入新測試檔與測試用 LINE 模擬）執行新增的 `smoke-r54-4-mbv2-hf1-c4-1-dedupe-resume.js`，再用同一份測試驗證 C4.1。數字見第 6 節。

### 1.1 必修一：匯入已受理紀錄後仍可能重複發送

**根因**：C4 只用「`claim=1` 的那一列」判斷同週期是否已通知（`claimFor()` → `evaluateRecipient()`），`requestNotifyState()` 也只看 claim。匯入時若本地已有占用名額的待發送列，`stepRestockNotify()` 依唯一索引把匯入的已受理列改為 `claim=NULL`；之後 `confirmBatch()`／`resumeBatch()`／`runBatch()` 都只看到本地那筆 claim 屬於自己的批次，因此用本地的 retry key B 再送一次。

**修正**：
- 新增 `cycleEvidence()`：**已受理證據**＝同店同週期任一列 `status='accepted'`，**不看 claim**、不分本地或匯入；另外，同週期**其他**列曾交給 LINE（`attempt_count>0`）且不是確定失敗 → 視為**可能已受理**（`possibly_notified`），不得再用另一把 key 送出。
- `evaluateRecipient()` 先判斷證據、再判斷名額占用（`claimFor()` 仍保留，用於「已在其他批次處理」）。預覽、確認、續送、每次呼叫 LINE 前都走同一個函式（worker 傳入 `ownDelivery` 排除自己這一列）。
- `blockConflictsRaw()`：在**匯入交易內**（`stepRestockNotify()` 結尾）與**服務啟動時**，把同店同週期已有受理證據、但本地尚未完成（pending／retry_wait／held／unknown）的列停止並標示 `already_notified`。不刪列、不改 retry key、不動已受理列；名額**保留**（讓只認 claim 的舊版程式回退後也不會再排入）。預覽匯入在交易回滾時一併還原。
- 已在網路上的請求：照實記錄回應；回應若為可重試，下一輪送出前的重新檢查會看到受理證據而擋下，不會啟動下一次重試。
- `requestNotifyState()`：有任一 accepted 列即回 `accepted`（不看 claim）；結果不明不算已受理。
- 唯一索引、歷史列、歷史 retry key 都未變更；沒有清空 claim。

**前後**：C4 上，匯入後手動續送，pending／held／retry_wait／unknown／匯入列本來就是 claim=NULL 的 5 位會員**各被再送 1 次**；worker 執行途中匯入，第二位仍被送出；在途請求逾時後仍以同 key 再送一次並受理。C4.1 上，這些會員新增的模擬呼叫皆為 **0**，列標示「本週期已通知」。

### 1.2 必修二：跨店匯入後續送仍帶來源店連結

**根因**：匯入只重新對應 `product_id`，批次的 `message_text`／`link_url`／`product_uuid` 仍是來源店（來源 LIFF、`store_id`、來源商品識別）；`resumeBatch()`／`runBatch()` 直接使用訊息快照送出，沒有驗證快照是否屬於目前店別。

**修正**：
- 新增 `batchContext()`：送出前驗證目前店別下，該商品仍存在、目前 `product_uuid` 與批次相同、用**目前**店別 LIFF 設定重建的連結與 `link_url` 完全相同、`message_hash` 與訊息相符且訊息含該連結。
- 不相符時（`voidMismatchedBatchRaw()`）：
  - 從未交給 LINE 的未完成項目（attempt_count=0）→ `blocked／link_mismatch`，**釋放名額**；
  - 曾嘗試、結果不明、已受理的項目**原樣保留**（狀態、claim、retry key、訊息快照都不變）——不改訊息沿用舊 key，也不換新 key 補送；
  - 批次改為終止狀態 `cancelled`（`pause_reason='link_mismatch'`）保留歷史，續送回 409 並說明原因。
- 套用在：確認（預覽後設定改變 → 作廢預覽、要求重新預覽）、續送、worker 每一輪。
- 店家在目標店重新預覽：使用目標店最新 LIFF、`store_id`、商品識別；重新通過同意與防重驗證。曾嘗試／結果不明的會員因 `possibly_notified` 或名額占用被排除，無法藉重新預覽繞過。
- 設定相符時完全沿用原 retry key 與原訊息快照（驗收 X9）。

**前後**：C4 上，跨店匯入＋顧客重新同意後續送，訊息帶來源店 LIFF 與 `store_id`；同店 LIFF 或商品識別改變後也照舊連結送出。C4.1 上 0 次呼叫、回 409；從未嘗試者在目標店重新預覽後，訊息正確指向目標店。

### 1.3 修正三：商品關閉收集後仍能發送

**根因**：`computePreview()` 讀取 `demand_collect_enabled` 只用於顯示；確認、續送、worker 都沒有檢查。

**修正**：新增 `productGate()`＝收集開關＋既有可訂購判斷，預覽、確認、續送、每筆送出前一致使用；關閉時排除原因為 `collect_disabled`（預覽 blocker 同名）。本人查看、取消登記、撤回同意不受影響；重新開啟不會自行發送；已受理與結果不明的歷史不變。

**前後**：C4 上關閉收集後仍可預覽發送、確認後送出、執行中關閉也會繼續送下一位。C4.1 上全部擋下（C1–C3）。

### 1.4 修正四：手動續送突破嘗試上限

**根因**：`resumeBatch()` 把 held／unknown 一律改回 retry_wait，不看 `attempt_count`；worker 的發送資格轉移也沒有檢查次數，所以每按一次續送就多送一次。

**修正**（`max_attempts`＝自動重試＋手動續送的**總上限**，不歸零、不提高既有紀錄）：
- `resumeBatch()` 只恢復 `attempt_count < max_attempts`、仍在 23 小時時間窗內、且沒有永久阻擋原因的 held／unknown；恢復前用同一套判斷重新檢查。
- `runBatch()`：選取條件與原子轉移（`UPDATE … WHERE attempt_count < max_attempts`）都檢查剩餘次數；舊資料中已用完卻仍是待重試的列先改為「結果待確認」（保留原錯誤代碼）；無法取得資格的列在同一輪不再重選，避免忙迴圈。
- `finalizeBatch()`：已用完次數的 held 不再算「待處理」，批次不會永遠停在暫停。
- 明細新增 `attempts_exhausted`／`max_attempts`，後台顯示「已達嘗試上限 n／n」。

**前後**：C4 上上限 1 的項目按續送後嘗試變 2 次並受理；上限 4 已用完的項目續送後變 5 次；舊資料中已用完的待重試項目也被送出。C4.1 上次數不增加、不呼叫，其他仍有剩餘次數的會員照常完成，批次在數百毫秒內收尾。

### 1.5 修正五：顧客畫面不能宣稱已收到

**根因**：`public/line-order.html` 的已通知說明寫「此登記已收到過補貨通知」。

**修正**：改為「此登記的補貨通知已交由 LINE 處理，同一次登記只通知一次。」後台維持「LINE 已受理」與「不代表顧客已收到或已讀」說明；結果不明（unknown）不顯示為已受理（`requestNotifyState()` 只認 accepted）。已檢查商品卡、登記管理、提示訊息、批次明細與文件。

## 2. 已受理證據與 claim 的判斷方式

| 判斷 | 依據 | 用途 |
|---|---|---|
| 已受理證據 | 同店同 `request_uuid` 任一列 `status='accepted'`（不看 claim、不分來源） | 本週期**永遠不再發送**（`already_notified`） |
| 可能已受理 | 同店同週期**其他**列 `attempt_count>0` 且 `status<>'failed'` | 不得用另一把 key 再送（`possibly_notified`） |
| 名額占用 | `claim=1`（部分唯一索引，同店同週期最多一筆） | 同時間只有一筆工作；其他批次排除為 `in_other_batch` |
| 本筆自己的重試 | 同一列、同一把 retry key | 受次數上限與 23 小時時間窗控管 |

檢查順序（`evaluateRecipient()`）：登記狀態 → 已受理證據 → 可能已受理 → 名額占用 → 本週期同意 → 取餐偏好 → 會員 → 好友；之後再檢查商品閘門（收集開關＋可訂購）與批次內容（連結）。

## 3. 匯入批次何時可續送、何時必須阻擋

| 情況 | 處理 |
|---|---|
| 同店、LIFF 與商品識別都未變（一般還原、重啟後續送） | 可續送，沿用原逐筆紀錄、原 retry key、原訊息快照 |
| 跨店匯入，或同店但 LIFF／商品識別已改變 | 拒絕續送（409）；從未嘗試者作廢並釋放名額；其餘保留；批次終止（`cancelled`／`link_mismatch`）；請在目前店別重新預覽 |
| 同週期已有已受理證據（含匯入的 claim=NULL 列） | 本地未完成列停止為 `already_notified`，不續送、不重新預覽 |
| 匯入的同意 | 仍需顧客在本環境重新確認（C4 規則不變） |
| 已用完次數或超過 23 小時 | 不續送，保留「結果待確認」，明細標示原因 |

## 4. 從未嘗試、已嘗試、結果不明、已受理的處理差異

| 狀態 | 被擋下時 | 名額 | 可否重新預覽納入 |
|---|---|---|---|
| 從未嘗試（attempt_count=0） | `blocked`＋原因 | 一般原因（撤回、停售、收集關閉、連結不符）**釋放**；已通知類原因**保留** | 一般原因可以（須重新同意等條件成立）；已通知類不行 |
| 已嘗試、確定未受理（401／429 等） | `blocked`／保留原狀 | 保留 | 不行（`possibly_notified`／名額占用） |
| 結果不明（逾時、5xx、中斷、非語意 409） | 維持 `unknown`＋原因 | 保留 | 不行 |
| 已受理（accepted） | 不動 | — | 不行（`already_notified`） |
| 確定失敗（400 等 `failed`） | 不動 | 保留 | 不行（名額占用） |

  4. 回退後必修一～四的保護會回到 C4 行為（例如之後再匯入已受理紀錄、手動續送上限），建議回退期間不要匯入補貨通知紀錄、不要開啟通知發送。
- 回退後再升級回 C4.1：正常啟動（R3），啟動時會再執行一次衝突掃描。

## 8. 測試站最短驗收（不發送真實訊息版）

本輪不呼叫真實 LINE，以下步驟在測試站維持「啟用 LINE 補貨通知發送」**關閉**即可驗證：

1. 部署 C4.1 到測試站，確認後台「LINE 補貨通知：尚未啟用」、點餐頁正常。
2. 後台想買登記 → 任一商品「查看」→ 關閉該商品收集 → 「預覽通知」：應顯示「商品已關閉想買登記收集」且不可發送（另會因通知未開啟而顯示不可發送）。重新開啟收集。
3. 若測試站有 C4 期間的補貨通知批次：打開批次「明細」，確認狀態文字只有「LINE 已受理／結果待確認／發送前已擋下…」，沒有「已送達／已讀」；已用完次數的項目顯示「已達嘗試上限」。
4. 顧客端「我的想買登記」中，已受理過的登記顯示「此登記的補貨通知已交由 LINE 處理，同一次登記只通知一次。」

真實發送的驗收（訂閱→預覽→對自己帳號單人發送→點連結→取消通知）仍依 C4 報告第 11 節，由你自行決定時間開啟與執行。

## 9. 已知限制與尚未驗證

- **尚未驗證**：LINE App／LIFF 真機、真實 Messaging API（真實權杖、配額、好友、送達）、正式 Zeabur、多台伺服器共用同一資料檔。
- 「可能已受理」採保守判斷：同週期其他列曾送出且不是確定失敗（含 401／429 這類其實未受理的情況）都會阻擋，這些會員本週期不會再收到通知。
- 跨店或連結改變後，曾嘗試／結果不明的項目不會補送；需要時由店家自行聯繫顧客。
- 退避時間以秒為單位保存（C4 既有行為，本輪未改）。
