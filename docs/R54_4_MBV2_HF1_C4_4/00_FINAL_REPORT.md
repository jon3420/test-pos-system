## 1. 根因

C4.3 的世代保護（`_pdMineGen`）只用在**本人查詢**（`/mine`）的回應：查詢送出後有異動，舊快照會被丟棄。但**異動本身的回應**（`_submitDemand()`、`_cancelDemand()`、`_revokeDemandConsent()`）沒有版本判斷：

1. **沒有「同一商品的最新操作」概念。** 每個異動回來就直接寫入本機資料：新增／修改把回應中的登記寫回 `_myDemands`，取消就刪除，撤回就改同意狀態。顧客在第一個請求還沒回應時關閉並重新開啟表單（新的 `_demandSheetState`，不在 `submitting`），就能發出第二個異動；第一個回應晚到時，會把較舊的結果寫回去。
   - 例：修改成 3 份（伺服器已寫入、回應晚到）→ 取消成功 → 舊回應把「3 份」寫回，畫面顯示「已登記 3 份」，資料庫卻是已取消。
2. **異動回應操作的是「目前的表單」，不是發起操作的表單。** 成功時呼叫 `_closeDemandSheetQuiet()`、失敗時 `_renderDemandSheet(錯誤)`，都作用在 `_demandSheetState`，因此會關閉或改寫顧客之後開啟的另一個商品（或另一位會員）的表單。401 經 `_handleDemand401()` 把目前表單改成「登入已過期」。
3. **檢查點不完整。** C4.3 只在 `apiFetch` 之後檢查會員是否切換；`_cancelDemand()`、`_revokeDemandConsent()` 在 `await resp.json()` 之後沒有再檢查，body 讀取期間切換會員，舊會員的取消會關閉新會員的表單並提示「已取消補貨登記」。
4. 舊異動被忽略時沒有機制確認伺服器最終狀態。

影響範圍：只有顧客點餐頁的補貨登記異動流程。後台、通知發送、資料層都不受影響。

## 2. 修正（`public/line-order.html`）

- **操作版本**：每次新增／修改份數、取消、撤回同意建立一個操作 `{ id, 店別, 會員 session, 商品, 發起的表單 }`，並記為該商品的最新操作（`_pdOpLatest[商品]`）。
- **每個非同步等待點之後都驗證**（取得 response 後、讀完 JSON 後、網路錯誤時）：店別相同、會員 session 相同、且仍是該商品的最新操作，才可以寫入本人資料、更新商品卡或提示。
- **較早的操作**（被同商品較新的操作取代，或會員已切換）：不論成功、失敗、401 或網路錯誤都不套用、不提示（`_pdOpStale()`）。所有重疊異動結束後，以**一次**本人查詢確認伺服器最終狀態（沿用 C4.3 的 `_pdMutEnd()`→`_pdReloadMine()`；同一世代的查詢合併，不重複、不持續重試）。
- **只改動自己的表單**（`_pdOpOwnsSheet()`）：成功只關閉發起操作的表單（若仍開著）；錯誤只顯示在自己的表單；不關閉、不改寫之後開啟的其他商品或其他會員的表單。顧客仍可隨時關閉表單、繼續點餐。
- **401**：只有目前操作才會把**該操作的 session**標成登入過期（C4.3 的過期旗標本來就綁定 session）。
- **失敗時依伺服器實際狀態顯示**：取消、修改或撤回失敗（含網路錯誤）時保留錯誤提示，並在異動結束後重新查詢；不誤報成功。修改遇到 403／404（例如商品剛關閉收集）時，改為異動結束後重新查詢，再在自己的表單顯示錯誤並轉為唯讀管理（C4.3 會在異動進行中發一個必然被丟棄的查詢）。
- **不同商品互不取代**：最新操作按商品分開計算。
- 撤回同意加上重複點擊防護，失敗時顯示錯誤（C4.3 失敗時沒有提示）。
- 未改動：伺服器規則（通知同意綁定登記週期，取消後重新登記為新週期、不沿用舊同意）、C4.3 的設定編輯版本、批次明細查詢順序、本人查詢世代保護、C4.2 首屏入口／自動更新／文案、C4.1 通知防重送／收集開關／跨店連結檢查／嘗試上限、Recovery／Handoff 還原保護。登記不建立訂單、不扣額度、不保留商品、不自動發送通知。
