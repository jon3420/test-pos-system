## 3. Cross-range Stale Fallback — Root Cause Detail

**Mechanism:** `geoGa4H1Refresh()` fetches rows for whatever range is
currently selected. On success, the payload was cached as
`geoGa4H1State.lastGoodPayload` with no record of *which range* it belonged
to. On the next failure (any failure — network error, backend error), the
code unconditionally reused that cache and displayed it, tagged only
`stale: true` in the status text.

**Why this matches the Manual QA symptom:** if a user selects range A (say,
7d), it loads successfully; the user then selects range B (say, 90d) and
that specific request fails (transient network issue, GA4 rate limit,
etc.) — the screen would continue showing range A's rows, dressed up as a
"stale" but ostensibly successful response for range B. The Table/Map never
visibly change, matching the report of "range buttons don't seem to affect
the table."

**Fix:** `_geoGa4H1FetchRangeKey(mode, opts)` builds an identity from the
transport mode *and* actual `startDate`/`endDate`. `lastGoodRangeKey` is
recorded alongside `lastGoodPayload`. Fallback is now gated:
`geoGa4H1State.lastGoodRangeKey === currentRangeKey`. Same-range transient
failures still gracefully degrade to the last good cache (allowed,
requirement §6 of the source spec); cross-range failures now render a
clean empty/error state (forbidden to fall back, requirement §7).

**Range-key collision risk, checked explicitly:** `90d`, `180d`,
`this_year`, `last_year`, `single`, and `custom` can all transport as
`apiRange==='custom'`. The key is **not** `mode` alone — it includes the
actual `startDate`/`endDate`, so these do not collide with each other even
though they share the same wire-level `range=custom` value. Verified by
Heatmap Range Runtime Part G (range-key collision guard) and static audit
Category F.

## 4. Overseas/Other — Root Cause Detail

**Classification: DISPLAY IDENTITY COLLISION, not persisted identity
collision.** `buildRawLocationKey({country, region, city})` already
produces a distinct key per distinct raw combination — two rows for, say,
Japan and the United States are two separate persisted rows with two
different `raw_location_key` values. The bug was that
`_geoGa4H1RowLabel()` collapsed both to the identical literal string
"Overseas／Other", making them visually indistinguishable in the Table even
though they were never the same underlying data.

**Fix contract honored:**
- `raw_location_key` is unchanged (persisted identity untouched).
- No `activeUsers` summation was added anywhere — each raw row keeps its
  own value; they are not merged into one displayed row.
- Display now appends available raw `country_raw`/`region_raw`/`city_raw`
  context, e.g. `Overseas／Other（Japan / Tokyo / Shibuya）` vs.
  `Overseas／Other（United States / California / Los Angeles）`.

## 5. Dashboard/Heatmap 1-vs-31 — Status: NOT REPRODUCED

This incident is **not** classified as fixed and **not** classified as a
confirmed pipeline defect. What has been established:

- The Data Lineage Runtime proves that for the **same exact range** (same
  `store`, `property`, `range_start_date`, `range_end_date`,
  `raw_location_key`), two independent reads of `getRangeGeoStats()` —
  simulating separate Dashboard and Heatmap requests — return **identical**
  `active_users` values, traceable to the same persisted row (`synced_at_utc`
  and `raw_location_key` both match).
- This means: given the *same* snapshot, the pipeline does not
  independently corrupt the value differently for each view.
- What is **not** established: what the actual `range_start`/`range_end`/
  `synced_at` were for the specific screenshots that showed Dashboard=1 and
  Heatmap=31. That incident's screenshots do not include enough metadata
  (visible date range for the Heatmap table at the time, `synced_at` for
  either view) to reconstruct which persisted snapshot(s) each number came
  from.

**Remaining candidate causes (no single one selected as root cause):**

- A. Dashboard and Heatmap were showing genuinely different date ranges at
  the time (the screenshots already show Dashboard's default 7d window as
  2026/08/04–08/10, one day off from the Google UI's manually-set
  2026/08/03–08/09 — a real, visible range mismatch in the evidence itself).
- B. The two views' `synced_at` differed (one stale relative to the other).
- C. One side hit the cross-range stale-cache bug described in §3 (fixed
  this round, but can't be confirmed post-hoc for that specific incident).
- D. The two numbers came from different persisted snapshots entirely.
- E. Marker/mapping coverage difference (a district appearing in one view's
  rows but not the other's marker set) — distinct from a value mismatch.

**Disposition:** `PRODUCTION INCIDENT — NOT REPRODUCED AS A SAME-RANGE
PIPELINE DEFECT.` Requires manual re-verification post-deployment with all
three surfaces (Google Analytics UI, POS Dashboard, POS Heatmap) set to the
*identical* custom date range and with `range_start`/`range_end`/
`synced_at` recorded for each — see the Reconciliation Report and Manual QA
document.

## 6. Out-of-Scope Finding (recorded, not fixed)

While building the Data Lineage Runtime fixture, a resolver edge case was
observed: when a raw GA4 row's `region` and `city` dimensions disagree
(e.g. `region` names one county while `city` names a district that actually
belongs to a different county), `normalizeGa4Location()` falls back to
county-level resolution using `region` and silently drops the district —
without flagging `ambiguous`. This is a real data-quality edge case in
principle, but:

- It was not observed in any of the Manual QA screenshots or
  reported symptoms.
- Fixing it would require design decisions (should city or region take
  precedence? should it flag `ambiguous` instead of `ok`?) outside this
  round's accepted fix set.

**Classification: OUT-OF-SCOPE DATA QUALITY EDGE CASE — FUTURE FOLLOW-UP.**
Not included in the H1.4.3 Production Diff. No code touched.
